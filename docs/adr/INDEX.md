# ADR Index — backlog and status board

This file is the live status board for the ADR series. Every load-bearing
decision in goat is either listed here as Accepted, drafted as
Proposed, or queued in the backlog. The rows of ADR 1234 and below are
kept by hand. A new ADR's row is rendered from the ADR file itself: see
"ADRs above 1234, rendered from their own files" below.

**Authoring order rationale.** The 0000 (meta) and 0100 (strategy /
accreditation) series are written first because they are read first by
new contributors and SCA-Rs. The remaining series are written in a
priority order that front-loads the highest-load-bearing decisions
(architecture, mesh, crypto, supply chain) and back-loads ADRs that
mostly recapitulate well-documented design decisions (the OS/hardware
and lifecycle ADRs).

**Status legend:** `Accepted` (live decision), `Proposed` (drafted, not
yet adopted), `Backlog` (identified, not yet drafted), `Superseded`
(replaced by a later ADR — see header).

**Diagram column:** 📊 means the ADR has an embedded diagram; the link
opens the rendered SVG directly. Sources for all diagrams live in
[`diagrams/`](diagrams/).

**Glossary.** Every ADR ends with a pointer to
`GLOSSARY.md` — a single alphabetized reference for the
acronyms and project-specific terms used throughout the series, each
linked to its authoritative upstream source.

## Sub-series tags

A **sub-series tag** is a cross-cutting label that lets a themed cluster
of ADRs be discoverable as a unit *without* forcing them out of their
natural numeric band. ADRs in the cluster keep their content-adjacent
numbers (an identity ADR stays in the 0400-series, a crypto ADR stays
in 0600, etc.) and add a bracketed tag prefix in the title cell:
`[<tag>] Title goes here`.

**Why tags rather than a separate numeric band.** Themed clusters
typically span multiple content bands (a security-ascent cluster
touches identity + crypto + supply chain + ops in one breath). Forcing
them into one numeric band either fragments the cluster across bands
anyway, or pulls ADRs out of the band where a future contributor would
look for them. Tags carry the cluster identity without disturbing the
numeric organization.

**Authoring rules for tagged ADRs.**

- The tag is permanent — once an ADR ships under a tag, the tag stays
  on the row even if the cluster's active authoring concludes.
- An ADR can carry only one sub-series tag. If a decision is genuinely
  cross-cluster, it doesn't belong in either cluster — write it
  untagged and link from both clusters' implementation trackers.
- The tag does not change ADR numbering. Number from the band's
  current tail; gaps reserved for future fill stay reserved.
- New tag → add a row to the "Active sub-series" table here in the
  same PR that introduces the first ADR carrying the tag.

## Authoring discipline

- New decision → add row here as Backlog → draft as Proposed → land
  as Accepted in the same PR as the implementation.
- Number gaps within a band are reserved for future fill — do not
  renumber to close them.
- Each row is one ADR. If a topic needs more than one, split it
  into adjacent numbers (e.g. `0801` and `0801a` is wrong; use
  `0801` and `0801`-extended or take the next free number).
- Repo scope is set at write time; revisit at split time
  (see [`0004`](0004-repo-scope-tagging.md)).
- When an ADR gains a diagram, mark its Diagram cell with
  `📊`. Source `.mmd` files live alongside
  the rendered `.svg`; rebuild with
  `mmdc -i <name>.mmd -o <name>.svg -b transparent`.

## Checkpoint protocol

The ADR series is large enough that authoring it takes multiple
sessions. To make resumption robust:

1. **This file is the resume point.** A new session starts by
   reading `INDEX.md`, finding the next Backlog row, and authoring it.
2. **Commit after every ~5 ADRs.** Each commit updates `INDEX.md`
   in the same change so the status board never drifts.
3. **Each ADR is independently complete.** No ADR depends on a
   later one being authored; "Related" links can point to Backlog
   rows.
4. **If a session ends mid-ADR**, leave the partial ADR as
   `Status: Proposed` and do not flip `INDEX.md` to Accepted until
   the next session lands the final version.
