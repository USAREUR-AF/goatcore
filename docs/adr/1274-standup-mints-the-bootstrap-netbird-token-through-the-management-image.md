## TL;DR (for a layperson)

Setting up a new goatnet has one step that still needs a person: signing in to the mesh dashboard and creating the first administrator key, which every later step uses. We automate that step. The key is made by the mesh software's own code, in a version of it that we already build and run with a small, recorded change. The key is written to the goatnet's secrets store and read back before it is switched on, so there is never a working administrator key that nobody holds. It never appears on a screen or in a log, running setup again never makes a second key, and the mesh records that the key was made. If we had chosen to write the key into the mesh's database ourselves, every mesh upgrade could silently break it; if we had kept the step manual, every new goatnet would keep waiting for a person.

## Context

Standup phase 11 is manual today (`standup.rs`, the two `MANUAL` rows for LAN and internet sites). A person signs in to the NetBird dashboard with the bootstrap password, re-runs `dashboard-deploy.yml` so its post-task promotes them to admin, creates the service user `svc-<site>-netbird-infra` with role admin, creates its personal access token, and stores the token as `<SITE>_NB_API_TOKEN` under the declared secrets posture. Phase 12 then mints every other NetBird service identity with that token. Gate row J7 asks for phase 11 with no manual step.

The design ([`goatbuilder-build-targets.md`](../design/goatbuilder-build-targets.md) §4.1) chose a new `ops/mgmt-host-bootstrap` verb that writes the service user and token into NetBird's database with raw SQL. It rejected a route through the management service because that "would need a modified NetBird management service", which it took to conflict with ADR 1248. Examining that design against the code the fleet runs showed two things. First, the raw-SQL route writes NetBird's tables behind its back: in the version the fleet runs (upstream v0.71.4), `users.name` and `users.email` are encrypted at rest with a key the verb does not hold, and any NetBird upgrade can add a column, change the token hash or move a field. Second, the premise was wrong: the fleet's management image (`ops/netbird/Dockerfile`, ADR 0301) already applies `service-user-token-bootstrap.patch`, a recorded ADR 1248 departure that adds `management service-user bootstrap-token`. It is listed with the other departures in [`upstream-netbird-wireguard-watch.md`](../design/upstream-netbird-wireguard-watch.md), with the retirement condition "an upstream equivalent" and not proposed upstream. That command mints a service user and token through NetBird's own store code. It prints the plaintext token to stdout, mints another admin token on every run, and writes no activity event.

The operator chose, on 2026-11-27, to fix that command and use it for phase 11, with the conditions below.

## Decision

Standup phase 11 mints the bootstrap NetBird identity (`netbird-infra` in `ops/netbird/service-identities.yaml`) with the fleet management image's own patched command, not with a raw-SQL writer and not by hand. These five conditions are part of the decision; a build that does not meet each one is not this decision:

1. **Founder only.** Only a site whose group_vars declare `goatnet_founder: true` explicitly mints it; a site that leaves it unset is refused, not taken as a founder (elsewhere the variable defaults to true). A joining site never runs the mint: where Spock replication is on, NetBird's `users` and `personal_access_tokens` tables replicate between sites, so a joiner's mint would add a second admin identity to the shared account. How a joining site's standup obtains the token it needs is part of the build; it is never a mint.
2. **No token on stdout or in any log.** The command runs as a one-shot container of the pinned management image, with one host directory mounted: `/run/goat-bootstrap`, root-owned, mode 0700, on the host's `/run` tmpfs (refused if it is not a tmpfs mount). It writes the plaintext only to a file there that it creates with `O_CREAT|O_EXCL`, mode 0600. No output stream, argument, environment variable, error message, trace span, Ansible variable, idempotency record or goatbuilder run record ever holds it. The operator side reads the file over SSH and pipes it into the store; it never becomes an Ansible variable.
3. **A re-run mints no second token.** Outside a rotation (below), the account holds at most one token for the bootstrap identity. The run reads state, not a ledger:
   - the service user holds its token and the store holds a copy that authenticates: nothing is done, and the run exits as already applied;
   - the service user exists with no token row (an earlier run stopped before the token was switched on): the run resumes from the pending file if it is there, or makes a new pending token if it is not. No token row exists, so this is not a second token;
   - the service user holds a token row and the store holds no copy that authenticates: refused. The way out is the rotation below, run by a person, never by the standup: it makes a new token, replaces whatever the store holds with it, and removes the old row.
4. **An audit event.** The command writes NetBird's own activity events for what it does (`ServiceUserCreated`, `PersonalAccessTokenCreated`, and the deletion of the old row in a rotation), as the dashboard path does, so the mesh's activity log shows the identity was made, by the standup, and when. A step whose event is not written fails, and the token is not switched on. The activity store is per site and is not replicated, so the record lives at the founder.
5. **A stored copy before the token is valid.** Making the token and switching it on are two steps. The first creates the service user and makes the token with NetBird's own code (its plaintext, and the token row with NetBird's hash of it), writes the plaintext to the file, keeps the token row beside it on the host (it holds only the hash), and saves no token row in the database. The operator side stores the value under the declared posture and reads it back, then pipes the read-back value to the second step, which refuses unless it is byte-equal to the pending plaintext and then saves the token row the first step made. Outside a rotation, a token that authenticates is therefore, by construction, the one the store returns, and its hash is NetBird's; inside one, every token that authenticates is held in the store under one of two names (below). A store that keeps an old value, or a read-back that differs, is a failure, and no token row is written. The host files are removed after the token row is saved, before the token is checked against the API.
   Every declared posture needs a write and a read-back. Value stores (env-file, git-crypt, sops) write through `posture.py` and read back through it; 1Password writes the item and the `.envrc.local.d` export as phase 12's `--mint` does, and the read-back is phase 12's own check of the item (`op item get --format json`) together with the envrc export, which is what a later run reads first; both must hold the new value. The postures that keep no store copy (openbao, vaultwarden, custom, where phase 12 writes only an envrc export, and `env`) are refused before anything is made, and their phase 11 stays manual.

Two requirements apply to the build: its tests run against the fleet management image (the digest `ops/pins/fleet-pins.yaml` pins), not only against stock NetBird; and each change that implements it gets an adversarial security review before merge.

The identity's name is the one the registry resolves (`svc-{goatnet}-netbird-infra` in `ops/netbird/service-identities.yaml`, or the goatnet's `netbird_service_user_names`), passed to the command as it is. Its token lives for 365 days, as phase 12's `--mint` does; `netbird-service-identities.py --live` flags one with under 30 days left.

**Rotation (renewal, and recovery from a token with no stored copy).** One path, run by a person as a deliberate command, never by a standup. It keeps the old token working until the new one is stored and read back, replaces the stored copy in every posture before the new token is valid, and at every point holds each token that authenticates in the store. The rotation window is steps 2 to 6; inside it, and only inside it, conditions 3 and 5 hold in the form stated here. "Authenticates" below means authenticates through the NetBird API as this service user, so a token of another identity never counts as the old one. In order:

1. Check the service user holds exactly one token row (the old one). Make a new pending token as the first step of condition 5 does: plaintext file and token row beside it on the host, no row saved. The old token still works.
2. Keep the old value durable: write the current stored value, which must authenticate, under a second name in the same posture, read it back, and only then go on. A crash from here to step 6 leaves the old token in the store under that name. If no stored value authenticates (the recovery case), there is nothing to keep and this step writes nothing. The second name is `<NAME>_PREVIOUS` (for example `ZAGROS_NB_API_TOKEN_PREVIOUS`) in a value store and as a second export line in the `.envrc.local.d` file; under 1Password it is a second field, `api_token_previous`, in the same `{goatnet}-netbird` item, beside the export line. Each is read back as the main one is. A `<NAME>_PREVIOUS` left by an earlier rotation follows one rule: one whose value no longer authenticates is replaced; one that still authenticates is refused, unless this run is resuming that same rotation (the service user then holds the token it names), in which case it is kept and this step writes nothing.
3. Replace the stored copy with the pending value, in every place the posture keeps it: the value store's entry (`posture.py` gains a replace for this one name; `set_values` keeps an existing value, by design, for every other caller), the `.envrc.local.d` export line (replaced in place, not appended), and under 1Password the item's field (created if the item is absent, edited if it is present). Each replace refuses unless the value it replaces is the old token, or a value that does not authenticate, so a rotation never overwrites a third, unknown token. Then read every place back: all must hold the new value. Anything else stops the rotation with the old token still valid and still stored under `<NAME>_PREVIOUS`, from which the person puts it back.
4. Save the new token row, in one transaction that checks the service user holds exactly the old row. The account now holds two token rows for the identity; this is the only path that allows two, and only until step 6. Both tokens are in the store: the new one under `<NAME>`, the old one under `<NAME>_PREVIOUS`.
5. Check the new token authenticates through the API (`--live`).
6. Retire the old token. The command lists every consumer the registry names (`ops/netbird/service-identities.yaml`). It does not run this step by itself: it asks the person to confirm once each consumer has been deployed with the new value, and its prompt says to deploy them only after step 5 has passed (before that, `<NAME>` holds a token that does not work yet). Consumers that this repository deploys are checked; the ones deployed from elsewhere (the `external_consumers` from goatstuff) cannot be, and the command says so by name. On that confirmation it deletes the old row, then removes `<NAME>_PREVIOUS` from the store. Each of steps 4 and 6 writes its activity event, and fails if it cannot.

The phase 11 build adds a doctor check that flags a leftover `<NAME>_PREVIOUS` outside a rotation.

Recovery from a token row whose stored copy is gone or dead is the same path: step 2 writes nothing, and step 3 replaces a value that does not authenticate, or writes the first copy (creating the 1Password item if it is gone).

**What it amends.** Two premises of earlier records change:

- [`goatbuilder-build-targets.md`](../design/goatbuilder-build-targets.md) §4.1 and §4.2, and row 6 of [`goatlite.md`](../design/goatlite.md)'s table: the route through `ops/mgmt-host-bootstrap` with raw SQL and "no NetBird fork" (and, in goatlite.md, a token seeded at first account creation). The route is now the management image's patched command. The patch was already listed as a departure (`upstream-netbird-wireguard-watch.md`, `ops/upstream/deps/netbird.yaml`; [ADR 1248](1248-goat-follows-stock-upstream-netbird-and-wireguard-and-retires-its-departures.md), itself Proposed, governs that list). Its retirement condition stays as recorded: an upstream equivalent.
- The rule that a NetBird service identity is minted only by an operator running `netbird-service-identities.py`, never as a side effect of a playbook ([`live-state-guard-scheduling.md`](../design/live-state-guard-scheduling.md), `ops/netbird/service-identities.yaml`). For the one bootstrap identity, the standup mints it, and condition 4's activity events are its audit record. Every other identity keeps the rule. Both places that state the rule name this exception.

With the manual row gone, nobody signs in to the dashboard during standup. The first person to sign in afterwards is promoted to admin by the existing promotion, so the rule for who becomes the first human admin does not change: the post-task in `dashboard-deploy.yml` (it acts where `site_admins` is declared) run again after that sign-in, or the `netbird-admin-reconcile` timer where it is installed. The build adds the step that runs it.

## Alternatives considered

- **A raw-SQL verb in `ops/mgmt-host-bootstrap`** (the design's route). No NetBird code change. It writes NetBird's tables without NetBird's code: it cannot encrypt `users.name` without the store's key, so it must write it empty and get every other column's shape right by hand, and every NetBird upgrade can break it silently. Rejected for that schema risk.
- **Keep phase 11 manual.** No new trust change. J7 stays unbuilt, every new goatnet waits for a person at phase 11, and the patch stays in the image unused. Rejected by the operator.
- **The patch as it is.** Already ships. It prints the token, mints a new admin token on every run and records nothing. Rejected: it fails conditions 2, 3, 4 and 5.
- **One step that mints and saves the token, then stores it.** Simpler. A failure between the save and the store leaves a working admin token that no store holds. Rejected for condition 5.

## Consequences

**Positive.** A founder standup runs from phase 1 to 15 with no person present. The token is made by NetBird's own code at whatever version runs, so its encryption, hash and format follow NetBird. A working admin token never exists without a stored copy. A re-run is safe. The activity log shows the identity's creation.

**Negative.** goatbuilder now mints the goatnet's first NetBird admin credential with no person present. Root on the management host could already do this by hand (it holds the database superuser), so this is a change in automation and in the path the token travels, not a new privilege; it is still a trust change, and it is reviewed as one. The departure in the management image now carries more weight, and moving to a later upstream NetBird must carry the fixed command with it. The plaintext is on the host's `/run` tmpfs (which can swap) for the seconds between the first step and the token row's save, readable there by root, and so by anyone in the `docker` group, which can act as root. A failed run can leave it there until the next run or a reboot. The token expires after 365 days, and nothing renews it automatically. A deployment that runs openbao, vaultwarden or a custom store keeps a manual phase 11 until that store keeps a copy. Rotation is new work in three stores (a replace in `posture.py`, in the envrc export and in the 1Password item, and the `<NAME>_PREVIOUS` entry), and while it runs the account holds two admin tokens for the identity. The old row is deleted only on a person's confirmation that each consumer has the new value; the consumers deployed from outside this repository cannot be checked by it, which is a known gap: confirming too early cuts them off. With no sign-in during standup, the first human admin is whoever signs in first afterwards, and the bootstrap password file stays on the host until then.

## Assessor view (SCA-R)

This automates the issue of a privileged, non-person credential (IA-4, IA-5, AC-2): the identity is declared in a registry, minted by the vendor's own code path, stored under the declared secrets posture before it is usable, and its creation is recorded in the mesh's activity log (AU-2, AU-3, AU-12). The plaintext is confined to one root-only tmpfs file for seconds and never logged (IA-5(7), SC-28); the tests search every captured output, in encoded forms too. Least privilege is not improved: the identity is an admin, as it was when a person made it, because NetBird has no narrower role that can mint the other identities. The residual risk is the short host-file window and the automation itself; compensating controls are the founder-only gate, the refusal to mint a second token, and the activity record.

## Trigger conditions for revisit

- Upstream NetBird offers an offline, non-interactive way to mint the first admin token: retire the patch (ADR 1248) and move phase 11 to it.
- NetBird gains a role narrower than admin that can mint service users and tokens.
- A later NetBird changes how service users or tokens are stored, so the patched command no longer applies or its tests fail against the fleet image.
- A secrets posture is added that cannot read a value back.
