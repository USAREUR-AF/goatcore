## 1. What this is for

One tool builds every machine in a goatnet. A machine is one **platform family** (hardware, and how it is prepared) carrying one **target type** (the role it plays). Each family and each type is a data file goatbuilder reads, so a new one is a new file, not new code. goatbuilder checks every machine's end state, however it was first set up.

| Concept | What it is | Examples |
|---|---|---|
| **Platform family** | Hardware that can play the same roles, and its preparation: firmware, boot media, the OS image, disk encryption and how it unlocks. The golden path lives here. A model joins a family; no target type names a model | host-class, cloud, small computer, ruggedized mobile edge |
| **Target type** | The role the machine plays in a goatnet: its plays, services and acceptance checks | core, obs, break-glass, network-gear jump box, octo-pod, Billie node, vendor gateway, first-bite, network tap, federation boundary, simple boundary, goat-processors, phone |
| **Service** | Software placed on a machine that already exists. It has a version, a play and a health check, and no OS, encryption or enrolment of its own. `goatbuilder deploy` places it; it is not a type (section 3.9) | the portal, goat-map, goat-feeds, the goat-processors runner |

## 2. What exists today (measured on `main`, 2026-11-23)

### 2.1 Three taxonomies for one question

Three places answer "what kind of machine is this", and none reads the others:

1. **`join-node`'s class list**, compiled in. `crates/goatbuilder/src/joinnode.rs:90` declares `CLASSES = ["core", "obs", "breakglass", "network-jump", "phone"]`. Each class has its own match arm, at `joinnode.rs:661` (core), `joinnode.rs:664` (obs), `joinnode.rs:680` (breakglass) and `joinnode.rs:686` (network-jump). Any other class is refused with GB-247 (`joinnode.rs:692`). A new kind of machine is new Rust.
2. **`standup`'s group_vars flags.** The founder standup does not read that list. It reads one flag per optional machine from the site's `group_vars`:
   - `has_obs_host` (`crates/goatbuilder/src/standup.rs:322`);
   - `has_breakglass_node` and `has_network_jump_node` with their absence reasons, ADR 1183's keys (`standup.rs:710` and `standup.rs:711`).
3. **The image builder's hardware classes.** `ops/bootstrap/hardware-classes.yaml` already keeps two axes apart: platforms (what an image is built for, from line 21, including `rpi5` at line 89) and roles (what a host becomes at first boot, from line 111: `core`, `obs`, `core-backup`, `obs-backup`, `breakglass` and `jumphost`). It already records that boot unlock is a platform property, because it depends on TPM presence (`hardware-classes.yaml:46`). goatbuilder does not read this file.

The three disagree in names (`network-jump` and `jumphost`), in coverage (the image roles have no `phone`, and `join-node` has no backup roles), and in what they carry: a play list in Rust, a flag in YAML, a purpose sentence in YAML.

### 2.2 Below the reachable host

No goatbuilder verb installs or checks an operating system. `ops/bootstrap/` holds the golden-path pieces, and goatbuilder calls none of them:

- an Ubuntu 24.04 autoinstall answer file with full-disk LUKS on LVM and key-only SSH (`ops/bootstrap/autoinstall/user-data.yaml:2`, `:28`);
- per-platform image builders (`build-image-orin.sh`, `build-image-karbon.sh`, `build-image-ec2.sh`; the `rpi5` platform's builder is `none-yet`, `hardware-classes.yaml:93`);
- the first-boot unit and its container integration test (`first-boot/`).

Today a person installs Ubuntu and sets up LUKS by hand, or runs these scripts, before goatbuilder's first phase. For the Raspberry Pi, `ops/rpi-base-image/` holds the numbered steps 00 to 05, from prerequisites to FIPS mode, with no step that verifies the built image or box; three builders that differ from one another exist outside goatcore.

## 3. The design

### 3.1 Platform families

One data file per family, under `ops/goatbuilder/families/`. A model joins a family by an entry in it: its firmware, boot media, OS image, disk-encryption shape and unlock, what it needs beyond the image, and its golden-path builder. `ops/bootstrap/hardware-classes.yaml`'s platforms become the models of these families, and its roles axis is superseded by the type files.

| Family | Models | Builder (golden path) | Status |
|---|---|---|---|
| host-class | Karbon 801, Karbon 802, Jetson Orin, Jetson Thor | `build-image-karbon.sh`, `build-image-orin.sh`; both are skeletons by their own headers | supported; suited to core, obs and other heavy or resilient roles |
| cloud | AWS EC2 | `build-image-ec2.sh` | supported |
| cloud | Azure Virtual Machines, Google Compute Engine | none | listed, not built |
| small computer | Raspberry Pi 5 today; a smaller OnLogic model later | the Pi base-image builder, `ops/rpi-base-image/` | proposed; the OnLogic model joins when the hardware is in hand |
| phone | none yet | none | built as data (`phone.yaml`), with no model entry |
| ruggedized mobile edge | TSI V3, TSI V3 mini | none: their own baseline | listed, not planned; goatbuilder only checks their end state |

**Each model's entry. Built:** the family schema (`ops/goatbuilder/schema/platform-family-v1.schema.json`) takes, for each model, its name and architecture, `firmware`, `boot_media`, `os` (the image, and the state of each Ubuntu release on the model: measured, built, designed, not built, not supported or unknown; 24.04 and 26.04 are always stated), `encryption` (`scope`: root, data, none or unknown; `unlock` and `recovery`), `extras` and `builder` (a path in this repository, or `none: ` and the reason), with `directions` where written directions exist. A family may still list bare model names, as an overlay's may; such a model delivers nothing that is known. goatbuilder reads the entries (`crates/goatbuilder/src/targets.rs`). Every value below is from the source the row names; a value no source gives is written unknown.

- **A microcontroller is no family (ESP32-P4, assessed 26 Nov). Designed, not built.** A board such as the ESP32-P4 runs firmware, not Linux: it has no memory management unit, so it can be no reachable Ubuntu host with an SSH key, the line goatbuilder builds from (section 3.5). It fits no family, and no target type names it. Its place is an attached device of one Linux goat node, which owns it, records it and speaks for it; that decision is proposed as ADR 1264 (pull request #1279, Proposed). Nothing in goatbuilder reads or checks such a device: whether `doctor --target` checks one through its parent node is for that ADR, not this family table.
- **The builder bar.** The team's Raspberry Pi base-image builder is the model for every family's builder: numbered, re-runnable steps from blank media to a verified machine (prerequisites, flash and verify the card, clone to NVMe, encrypt the root filesystem in place with LUKS2 using FIPS-approved primitives, enrol a YubiKey or removable-key unlock, enable FIPS mode, provision the substrate, verify the image, verify the box), each step proving its result before the next. The host-class and cloud builders are measured against it, and gaps are filed against each.
- **One Pi preparation.** The Pi base-image builder is the small-computer family's golden path. The two other Pi preparations fold into it: an SD-card seed that installs itself to NVMe with a YubiKey FIDO2 unlock, and the Clevis-and-Tang network unlock proposed in `hardware-classes.yaml:92`.
- **Encryption scope** is split between family and type. Each model's entry declares the scope its preparation delivers and how it unlocks; the table above has them. Unlock is a property of the hardware (`hardware-classes.yaml:46`); how much must be encrypted is a property of the role. The type declares the minimum scope its role requires, and `doctor --target` checks the scope a machine delivered. **Built:** a type that requires a scope accepts only families at least one model of which delivers it; any other is refused when the files are read (GB-425), and an unknown scope delivers nothing. A family's models can differ: the Jetsons encrypt a data volume and the Karbons the root, so a type that requires an encrypted root accepts host-class for its Karbons. `doctor --target`'s encryption row names, from the entries, which of the type's families' models prepare the scope and which do not. Not built: a machine declares its family, not its model, so which model a machine is is not checked; for a family of one model, the small computer, `doctor --target --live` reads the scope on its disk (section 3.5), and for any other family it is not checked.

### 3.2 Target types

One file per role: `ops/goatbuilder/targets/<type>.yaml`. `standup`, `join-node` and the image tooling all read it.

```yaml
# ops/goatbuilder/targets/breakglass.yaml (sketch; the schema is part of the foundation)
type: breakglass
families: [small-computer]             # the families this role accepts; never a model
encryption: root                       # the minimum scope this role requires (section 3.1)
os:
  - ubuntu: "24.04"
plays:                                 # in order; the same plays join-node and standup run today
  - play: mgmt-host-baseline.yml
  - play: breakglass-nodes.yml
    group: "{site}_breakglass_hosts"
services: [netbird-client, oob-overlay]
acceptance:                            # rows in the acceptance catalog, by token
  requires: [breakglass]
proof:
  ci: vm                               # a VM from a fresh cloud image (section 3.6)
  hardware: required                   # a recorded run on real equipment
```

| Group | Type | What it does | Families |
|---|---|---|---|
| host site | core | management plane: mesh control, identity, fabric router; A and B pair | host-class, cloud |
| host site | obs | observability and storage; A and B pair | host-class, cloud |
| access | break-glass | entry into the site's goat machines when the mesh and control plane are both down | small computer or host-class |
| access | network-gear jump box | entry into the site's network gear only (switches, routers, out-of-band management); not a general jump host | small computer (a Thor serves today) |
| edge | octo-pod | edge gateway: takes in feeds, records and audits them, releases chosen feeds to the fabric | small computer or host-class |
| edge | Billie node | runs the sensor kit's relays for the sensors wired to it (section 3.4) | small computer |
| edge | vendor gateway | runs the vendor bridges, one package per vendor (ADR 1255) | small computer |
| edge | first-bite | decodes binary messages from a network tap and hands them to authorized software | small computer or host-class |
| edge | network tap | records one Ethernet link, and may hand chosen traffic to a decoder; it decodes nothing (section 3.8) | small computer or host-class |
| boundary | federation boundary | the edge router that peers with another goatnet | small computer or host-class |
| boundary | simple boundary | sends selected data out to a partner receiver | small computer or host-class |
| processing | goat-processors | correlation, fusion, filtering and quality on translated data | host-class |
| (existing) | phone | a phone as a full core joiner ([phone-node.md](phone-node.md)) | phone |

Two kinds of machine have no type:

- **Relay and bridge hosts** are cloud machines that Terraform creates and their own plays configure. Gate J28 holds those plays to a goatbuilder verb or a listed reason.
- **A moon pod** is a learning tool and not a machine of a goatnet ([ADR 1239](../adr/1239-a-moon-pod-is-a-learning-tool-and-not-a-sovereignty-guarantee.md)).

- A type's `services:` names components (section 3.9). Its build installs them, and `doctor --target` checks them.
- `join-node --class <type>` accepts any type that has a file. `standup` builds a site's declared machines from the files of their types.
- The site still declares which machines it has, with ADR 1183's keys. A site's declaration says *whether*; the type file says *what*.
- Where a type accepts two families, the machine's declaration picks one, by load, resilience and ruggedization.
- **A type names families, never a model.** No type assumes a Raspberry Pi.
- **Edge kinds keep their own installers.** A type whose software has its own repository and installer (octo-pod, the sensor kit, first-bite, the vendor bridges) has plays that call that installer at a pinned, signed release and check its result. goatbuilder does not reimplement it. The type file names the repository and release as data.
- **octo-pod (built in part).** `ops/goatbuilder/targets/octo-pod.yaml` is the type: families small-computer and host-class, `encryption: root` (a pod keeps its recordings). `join-node --class octo-pod` builds it by push. Its phase 13 names the release component `octo-pod` (section 3.9), as the network tap names goatrope: where the pins have a release pin of it for the pod's group, phase 3 runs `goatbuilder deploy --dry-run` for it and phase 13 runs its play, `ops/ansible/octo-pod-deploy.yml`, found by the component's name; where they have none, phase 13 is a declared skip that says which pin is missing, and the machine is not a pod. octo-pod publishes one architecture-independent package and signs its checksums file with its release workflow, so the component's `release:` names the same `.deb` for amd64 and arm64, and its signer is `https://github.com/USAREUR-AF/octo-pod/.github/workflows/release.yml`. The package's name carries its version, so a new pin changes the declaration with it. The play calls octo-pod's own installer and reimplements none of it: the `release-file` role puts the verified package in place and writes the ledger row; apt installs exactly that package (again when its version is installed already), with its dependencies from the host's package sources, and the version dpkg reports must be the package's; then `octo-pod bootstrap`, `octo-pod init --pod <machine>` for a pod with no identity (the machine's inventory name; that it is also the machine's mesh peer name, as octo-pod requires, is not checked), `octo-pod apply`, and `octo-pod verify`, which must pass. goatbuilder verifies the package, and through it the images the package pins by digest; what octo-pod's own steps fetch besides is octo-pod's to verify. A pod that has an identity keeps it, and one whose identity is incomplete is refused. When the install or the pod's own steps fail, the play removes the component's `current` link before it fails, so `verify` reports the host not converged. A rollback is the same play: the role switches to the package before, apt installs it, and the pod converges again; the pod's identity and what it kept stay as they are, as octo-pod's own rollback leaves them, so its row declares `owns_state: true` and `rollback: pin-revert`. octo-pod 0.6.0 names its Zenoh image by a short name, which podman on a published Ubuntu 24.04 image does not resolve, so a host needs a container search registry; without one, `octo-pod apply` fails and so does phase 13. The public pins carry no octo-pod row, because any row changes the signed intent of every goatnet (section 3.8); a deployment with pods adds it in its own pins. `doctor --target octo-pod --live` reads on each pod whether it installs security updates by itself: the type file lists `checks: [automatic-updates]`, and the row holds the machine to the `unattended-upgrades` package installed and its service enabled, the `apt-daily` and `apt-daily-upgrade` timers enabled and running, and `APT::Periodic` asking for both; a fact it cannot read is UNKNOWN. The CI-tier run fails that check: when it runs, the VM's `unattended-upgrades` service and both `apt-daily` timers are masked, and the run has no join-node phase 14, which unmasks and starts the timers. Not built: `doctor --target`'s other checks on the machine; a fabric slot for the pod (it captures and keeps locally and releases no feed until its owner gives it one), the air-gapped install (octo-pod's images bundle; the pod pulls its images), a pod's sensor declarations, an arm64 run, and the pull converger (after 1.0).
- **first-bite (built in part).** `ops/goatbuilder/targets/first-bite.yaml` is the type: families small-computer and host-class. `join-node --class first-bite` builds it by push. Its phase 13 names the release component `first-bite` (section 3.9): where the pins have a release pin of it for the machine's group, phase 3 runs `goatbuilder deploy --dry-run` for it and phase 13 runs its play, `ops/ansible/first-bite-deploy.yml`, found by the component's name; where they have none, phase 13 is a declared skip and the machine decodes nothing. first-bite signs no checksums file: each of its archives carries its own GitHub artifact attestation by first-bite's release workflow at the tag, so the component declares `release.bundle: attestation` and its signer `https://github.com/USAREUR-AF/first-bite/.github/workflows/release.yml`, and names the `linux-gnu` archive for each architecture. The pin fixes the unsigned `SHA256SUMS` by its digest. The play calls first-bite's own installer and reimplements none of it. A machine declares, in its host_vars, `first_bite_interface` (the interface it captures on) and may name in `first_bite_dictionary` one of the dictionaries the release carries; a missing or malformed value, or a dictionary the release lacks, is refused (GB-415). The `release-file` role puts the verified archive in place and writes the ledger row. The play then checks that each member of the archive is a plain file or directory under its own top directory, unpacks it, held by root, beside the archive, and runs the archive's `deployment/install.sh --interface <it> [--dictionary <the release's dictionary>]`. first-bite's installer keeps a settings file it finds, so the play then reads it: it must capture on the declared interface and, when a dictionary is declared, decode with the installed one (GB-416). Last, the service must be running with no restart after a settling time. When any of these fails, the play removes the component's `current` link, so `verify` reports the machine not converged; after a failed rollback it keeps the file it rolled back to as `previous`, so a second rollback goes there again. Not built: a rollback run, old unpacked releases removed, a dictionary removed from a machine (the installed one stays), an arm64 run, `doctor --target`'s checks on the machine, and a network tap handing first-bite its traffic (section 3.8).

| Step | What happens | Today |
|---|---|---|
| 1. Declare it | the machine in the site config: its family and model, its type, and for a Billie node its sensors | group_vars and inventory |
| 2. Install the OS and disk encryption | scripted on a known model (the family's golden path, `goatbuilder image <model>`), or by hand from written directions | by hand, or `ops/bootstrap` scripts goatbuilder does not call |

### 3.4 The Billie node and the sensor kit

A **kid** is an integration component and nothing else: one small process that decodes one sensor's native output and converts it to ASTERIX, CoT, ISA or SAPIENT. A sensor may have several (tracks, status). Fusion and correlation are not the kit's job. A **Billie node** is the small computer that runs them, with the kit's local services: its own local router that never federates, a client session to the goat fabric, a one-way bridge from one to the other, a translator and a health publisher.

Three lines of the kit exist today, and none installs the way the kit's original design says (measured 2026-11-19 from each repository's code):

| Line | Status | How relays reach a machine | Joins the goat fabric | Hardware |
|---|---|---|---|---|
| Original design | not changed since 2026-09-01; its Pi deployment has moved to the prototype | one package with every relay on every node; an activation list turns on the node's relays (its ADR 0104) | — | Pi |
| Prototype | a feasibility spike (charter Proposed); the working Pi deployment today | the operator composes the relays each node gets; images built on the Pi or a laptop; a LAN scan starts only relays whose sensor is found live, unless marked external | NetBird enrolment; Zenoh mTLS from the fabric operator's bundle | Pi 5, arm64 |
| Public platform (`open-billie`) | a sensor-neutral rewrite; release 0.3.0 in preparation, not yet tagged; nothing signed yet | a platform `.deb`, then one bundle per sensor and architecture: `billie kid install`, `configure` (transport, bind address, port, source range), `activate`, with `upgrade`, `rollback`, `deactivate`, `remove` | NetBird optional; Zenoh mTLS from operator-supplied certificates | Ubuntu 24.04, arm64 and amd64 |

**Both methods are supported (open question 1, decided by the operator, 23 Nov).** goatbuilder installs the kids on a Billie node, and the kit's own `billie` commands stay supported on their own, with or without goatbuilder. goatbuilder follows the public platform's model and calls those same commands: it is the only line with a per-machine command set goatbuilder can call and check, and per-machine selection is what both newer lines already do. A node set up with the `billie` commands alone is checked by the same end state (section 3.5). Before goatbuilder relies on the platform, the platform needs a tagged, signed release and signed relay bundles. Under it, a Billie node's declaration lists each sensor with its parameters (transport, port, bind address on the sensor interface, source range, identifiers), and the type's plays install the platform at its pinned release, issue its fabric certificates, then install, configure and activate each declared sensor's bundle. Acceptance: the platform's own verification, a health sample round trip through the site fabric, and each declared sensor's relays running. Authoring a relay stays with the sensor's owner and the platform's own tool.

**Ubuntu 24.04 and 26.04 are both supported (open question 4, decided by the operator, 23 Nov).** A Billie node's type accepts both. What each part supports today, from its own repository:

| Part | Ubuntu today |
|---|---|
| Public platform (`open-billie`, 3ad730f) | 24.04 only, arm64 and amd64. Its bootstrap play refuses any other version, so a 26.04 Billie node waits for the platform to support 26.04 |
| Prototype | no version check; its one recorded node run is on 24.04, arm64. 26.04 is not measured |
| Original design | 26.04 is its standard Pi baseline, and its deploy role was re-verified on a 26.04 Pi (2026-08-01). It was written against 24.04 |

Running relays on types other than the Billie node is not decided (open question 3): the kit's platform brings its own local router and container runtime, which would meet goat's own router on a host-site, access or boundary machine, and it supports Ubuntu 24.04 only, not the Jetson OS.

### 3.5 Check the end state; guide the method; never put it on rails

The contract starts at **a reachable Ubuntu host with an SSH key**, however it was installed. Above that line, goatbuilder builds. Below it, goatbuilder guides, and it checks the result.

- **`goatbuilder doctor --target <type>`** checks a host's end state against its type and family, whatever path built it, and changes nothing. For example:
  - the encryption scope the type requires is in place;
  - the OS version is one the type accepts;
  - chrony starts before docker;
  - the docker data root is on the tier the type declares;
  - the inotify floor is met;
  - for a small computer, first boot completed and key-only SSH;
  - for a break-glass node, ADR 1114 §5's dual-homing contract.

  Every refusal names what to fix on the machine, not which installer to use. For a family goatbuilder does not prepare, such as the ruggedized mobile edge, this check is the whole of goatbuilder's part below the line.

  **Built: the base check**, `goatbuilder doctor --target <type> --site <site> [--node <machine>]`. It reads the checkout and reaches no host: the type, the platform family each of the site's machines of the type declares (accepted, refused with GB-376's words, or not declared and so not checked), and that the type's plays are in this tree. The machine's end state, every item in the list above, is a row that says it is not checked yet.

  **Built: a small computer's end state**, with `--live`. Each machine of the type that declares the `small-computer` family is read as root over Ansible (`ops/scripts/small-computer-endstate.py`, which reads and changes nothing, and ignores its two test variables when run as root) and held to what its model delivers: the model's entry in its family's file (section 3.1), with an `end_state:` for what the entry does not otherwise say: the board, the root's disk and where FIPS mode holds (`crates/goatbuilder/src/small_computer.rs`; an entry that cannot be read is GB-410). One row each:
  - the Ubuntu version (each the entry lists, unless `not supported`: for `rpi5`, 24.04 or 26.04; a 26.04 machine passes, and its row says the builder's steps install 24.04 only);
  - the board and architecture;
  - the root on LUKS2 on the model's disk (NVMe), the active mapping LUKS2 and running the header's cipher; the root alone is read, not other mounts or swap;
  - the header's primitives: an encrypted segment and nothing but encrypted segments, AES-XTS with a 256- or 512-bit key, every keyslot PBKDF2 with SHA-256 or longer and its area AES-XTS, SHA-2 digests, no unfinished reencryption;
  - every way the root unlocks at boot, each one the model delivers: for `rpi5` a YubiKey challenge-response (its keyscript and `ykchalresp` in the initramfs, and a second keyslot for the recovery passphrase), the passphrase at the console, the passphrase over SSH into the initramfs (`03b`'s dropbear), or a key on removable media read by `passdev`, the entry's four. Anything else found is refused: a Clevis or other token in the header, a key file in crypttab or the initramfs, a `.lek` key file left on the boot partition (`/boot/firmware/*.lek` and `/boot/*.lek`, when mounted), another keyscript. A crypttab whose entries name another device is unknown;
  - FIPS mode: the OpenSSL FIPS provider active and `fips=1`; the Pi's kernel has no FIPS mode, and the row says so. Whether OpenSSL's default properties hold programs to the provider is reported, not required: the builder activates the provider beside the default one and sets none, so on the builder's Pi MD5 still computes, and the row says that;
  - SSH key-only (no password, keyboard-interactive, host-based or GSSAPI login) with the builder's FIPS-approved algorithms alone; a `Match` block makes the row unknown, since `sshd -T` with no connection does not show what it changes;
  - cloud-init's first boot finished, with sudo working.

  A fact not read is unknown, never a pass. The FIPS-approved lists are the builder's (`encrypt-rootfs.sh`, `05-enable-fips.sh`), not a model's. Measured: `tests/small_computer_live.rs` runs the real collector, through the binary, against a stand-in machine whose LUKS2 header the real `cryptsetup` made with the builder's parameters (`tests/fixtures/small-computer/machine.sh`). Not measured: a real Pi. Not read: the dropbear server's own algorithms, and an `Include` beyond `sshd_config.d`. The other end-state items in the list above are not built.
- **The golden path, optional:** `goatbuilder image <model>` wraps that model's builder. It produces an install ready for step 3: the OS, the model's encryption, first boot.
- **The supported general path:** written directions for each type that state the intent and the end state, for a capable person on hardware the golden path does not know. `doctor --target` is how that person knows they arrived.
- **What goatbuilder does not do:** it is not an operating-system installer or configuration manager beyond the golden path. It does not partition disks, choose kernels or manage packages outside a type's plays.

### 3.7 Network gear

Each site's switches and routers connect its machines to each other and the site to its transport. goatbuilder does not configure them. It reaches them only through the network-gear jump box, and every machine it builds depends on them.

### 3.8 The network tap

A network tap is a machine, usually a small computer, with two wired interfaces for the link it records, and a third interface for its own management. It comes in two modes, and **only one of them fails open**.

| Mode | How it is connected | While the machine is off, restarting or broken |
|---|---|---|
| **listen** (passive, fail-open) | beside the link. A tap device or a switch mirror port carries the link and hands the machine a copy | the link is not affected; only the recording has a gap |
| **inline** (fail-closed) | in the link. The machine bridges its two interfaces, and every frame passes through it | **the link is down** |

A small computer that bridges two interfaces is always inline, and no software setting changes that: when its processor stops, nothing carries the frames. Failing open is a property of the device that carries the link. In listen mode the machine only receives.

The operator asked for a passive, fail-open tap, and decided (23 Nov) to "fully support the rpi setup" now and "improve the hardware used to build the tap in the future". So the Raspberry Pi tap is supported in both modes, and fail-open hardware for links it bridges today comes later:

- **A machine's declaration states its mode.** There is no default, and a declaration without one is refused.
- **Listen declares its source:** `copper-tap`, `bypass-relay` or `mirror-port`. A passive copper tap gives one output for each direction, which is what the two wired interfaces are for. A mirror port needs one. `bypass-relay` is a separate device that keeps the link closed and hands the machine a copy; a machine bridging behind a relay is inline, because the link is interrupted while the relay switches.
- **Inline is supported and declared.** `mode: inline` is the statement that the link drops whenever the machine does. `doctor --target`, `status` and the run record print `inline, fail-closed` on that machine.

```yaml
# a machine's declaration (sketch; the schema is part of the foundation)
tap:
  mode: listen                 # listen | inline; required
  source: copper-tap           # listen only: copper-tap | bypass-relay | mirror-port
  ports: [tap0, tap1]          # never the management interface
  management: mgmt0
```

**What the end-state check reads**, in both modes unless it says otherwise:

- no IPv4 or IPv6 address on a tap port or on the bridge, with IPv6 disabled and no DHCP, router advertisement or LLDP sent;
- management, the mesh and the default route on the third interface. An install that would take the interface carrying the operator's session is refused;
- listen: no bridge holds a tap port, and the ports' egress is dropped, so the machine sends no frame;
- inline: one bridge of exactly the two ports, STP off, forward delay zero, and LLDP frames forwarded;
- receive offloads and Energy-Efficient Ethernet off on the tap ports, and the declared link speed. A passive copper tap runs at 100 Mb/s, so a link that must stay at 1 Gb/s takes a powered tap device that closes the link when its power fails, or a mirror port;
- recording on a port, not on the bridge device: once the bridge has learned both addresses it passes frames from port to port, and the bridge device does not see them;
- boot waits for no tap port, a hardware watchdog restarts a hung machine, and the recording is a bounded ring on an encrypted root.

**Root encryption is required for a new tap.** The type's minimum encryption scope is `root`, and `doctor --target` refuses a tap whose root is not encrypted. The Raspberry Pi tap already in service was built before this and has no encrypted root; the operator decided (23 Nov) that future taps are encrypted and that this one stays in service as it is.

**Built and measured.** An installer for a Raspberry Pi 5 exists outside the public repositories, with an inline mode and a one-port listen mode. These results are from its inline mode, with the Pi bridging two laptops:

| Measured | Result |
|---|---|
| Datagrams at the receiver that were also recorded on the Pi | 1381 of 1381, none extra; the two captures agreed within 1.0 ms |
| Gap in the received datagrams across one power cycle of the Pi | 39.0 s (37 s by a ping each second) |
| After the power cycle | the bridge, both recordings and the forwarder came back with no one touching the Pi |

Not measured: any listen-mode source on hardware, and a hung machine as opposed to a powered-off one. Not built: recording two ports in listen mode, and the egress drop.

**Built in goatcore: the type and the mode declaration.** `ops/goatbuilder/targets/network-tap.yaml` is the type (families small-computer and host-class, `encryption: root`, `declares: [tap]`). A machine of it declares `tap:` in its host_vars as sketched above, read by `crates/goatbuilder/src/tap.rs`: no mode, a source on an inline tap, none on a listening one, a port count that does not fit the mode and source, management on a tap port, or `tap:` set in more than one of the machine's host_vars files (which one Ansible applies is its own precedence, so a second is refused rather than guessed at) is refused before any phase (GB-380), by `join-node` and by `doctor --target`. Both print the machine's line, `inline, fail-closed: ...` or `listen from a <source>, fail-open: ...`. `doctor --target` names the encryption scope and reports it UNKNOWN, a row that is not a pass, because it reads only the checkout. The type's phase 13 names the release component `goatrope` (section 3.9). Where the pins have one for the tap's group, `join-node` runs `goatbuilder deploy --dry-run` for it in phase 3, before anything on the machine changes: every check deploy makes before a host (fresh source, ladder, digest GB-382, signed intent GB-383, the release's fetch and verification GB-381, secrets), so join-node installs nothing deploy would refuse, and runs the component's play in phase 13: its own `deploy_playbook`, else `release-file-deploy.yml`, which puts the file in place and starts nothing. Where they have none, phase 13 is a declared skip that says which pin is missing. goatrope publishes signed releases (0.1.0 and 0.2.0: one archive for both architectures and a cosign bundle over its checksums file), and its play runs from its own archive (`release.play`, below). No public pins row declares it, so a goatnet declares the component in its own pins; where none does, a machine joined as `network-tap` is not a working tap. No site key declares a tap, so `standup` builds none. `status` prints each tap's line from the checkout.

**Built: the end-state check on the machine**, `doctor --target network-tap --site <site> --live`. `ops/scripts/tap-endstate.py` runs on each tap over Ansible, reads and changes nothing, and `crates/goatbuilder/src/tap_machine.rs` holds what it read to the machine's declaration: every item of the list above but two. A fact that could not be read is unknown, and unknown does not pass. Not checked: the recording's bound, which nothing declares, and a declared link speed, which the declaration does not carry (a copper tap above 100 Mb/s is refused, and the speed is printed). The egress drop is accepted as an nftables netdev egress chain or a traffic-control egress filter, whichever the installer uses; a program that bypasses the queueing layer is not caught by the second. Whether boot waits for a port is read from its systemd-networkd file only. Tested on real links in a network namespace (`tests/tap_machine.rs`); not run on a tap.

**Where a release component's play runs from (built): its own verified archive.** goatrope's play and role live in goatrope's repository and in its release archive, and not in goatcore; its component would say `release.play: deploy/ansible/goatrope-deploy.yml` (no public pins row has one; see below). The driver verifies the archive (digest, signature, checksums), unpacks the play's directory from those bytes on the operator's machine, and imports it through `ops/ansible/release-archive-play.yml` (`crates/goatbuilder/src/release_play.rs`). What is on disk is held to the archive on every run, so a play never runs from a file that is not the verified one. Beside the play stand links to the checkout's own group_vars, host_vars and roles, which is where Ansible looks. Refused (GB-381, check `play`): an archive that brings its own group_vars or host_vars, a role goatcore has, Ansible code of its own (`library`, `module_utils`, `collections` or a `*_plugins` directory beside the play or in a role), a link or anything but a plain file or directory, a path outside its directory, and two names that are one where case is ignored. Every play of the file must say exactly `hosts: "{{ target | mandatory }}"` and import no other, as Ansible reads the YAML. It runs on every architecture's one archive. When `release-archive-play.yml` is missing, both drivers refuse; neither runs another play in its place.

**What the refusals are not.** They keep the archive's files its own and keep it from replacing goatcore's roles, modules and variables. They are not a sandbox. The play runs with the operator's whole authority: as root on the target group, and, through `delegate_to: localhost`, a lookup or a task on another host, as the operator on the operator's machine with the credentials `ops/scripts/with-aws` gives the run and the SSH access that reaches every host. A `release.signer` is trusted with that much, and a reviewed change of the pin is a review of the play it carries. Variables the play sets itself (`vars:`, `set_fact`) outrank group_vars, as in any play.

**Rollback** runs the play of the release the pin names, with `release_file_rollback=true`, because that play knows what its own install did. A release that is not trusted is not rolled back with its own play: pin the earlier release and deploy it, which runs that release's play.

Considered and not chosen: an overlay or assemble entry, or a `source:` commit (section 3.10), pinned beside the release. Either is a second pin that must move with the first, and neither is covered by the release's signature: the play of one release could run with the software of another. With the archive's own play there is one pin, and a rollback's play is the pin's own. Not covered: a secret that the archive's play reads from the environment is not listed before the run, because the play is not in the checkout, and `rollback` verifies the pin's archive first, so it needs the kept files or a mirror. Measured in a VM, amd64 and arm64: join-node phase 13 runs goatrope 0.2.0's play from its verified archive, on an inline tap and again on a listening one (`ops/e2e/vm/types/network-tap.sh`). Not run: `deploy`, `deploy-component.sh` and `rollback` of such a component on their own.

**Software.** Two things are separate, and a tap needs only the first:

- **The machine:** the ports, the bridge, the watchdog, the recording ring and the end-state check. first-bite is not its home: first-bite reads a copy and never transmits on its capture interface, and an inline tap transmits every frame of the link. The machine's installer is a public repository of its own, usable without goat, with its own releases and owner, named `goatrope` (the operator's decisions, open question 5). Its owner is open. Besides the machine, `goatrope` covers decode-and-send and a relay role. A relay transmits on the link, so listen mode's rule that the machine sends no frame does not hold for it; how a relay is declared and checked is not designed. goatbuilder calls it at a pinned, signed release, as for the other edge kinds (section 3.2).
- **What reads the recording:** first-bite, as a service the machine may run (`mind --tap-only`, or a decoder). It is not part of the type.

### 3.9 Services on a machine

A machine target type and a service answer different questions, and a service never becomes a type because it needs deploying.

| | Target type | Service |
|---|---|---|
| Answers | what is this machine? | what runs on it? |
| Holds | families, OS baseline, encryption scope, enrolment, plays, acceptance | a version, a play, a health check, where it may run |
| Declared in | `ops/goatbuilder/targets/<type>.yaml` | a component of `ops/pins/fleet-pins.yaml` |
| Built by | `standup`, `join-node` | `goatbuilder deploy` |

- **A service `goatbuilder deploy` already covers needs nothing new.** Section 2.4 lists them.
- **A new artifact type, `release`,** holds a service that ships as a file and not as an image. The component declares its repository, tag, file per architecture, SHA-256 digest, and the signer its signature or attestation must name. The drivers fetch the file on the operator's machine, verify it, and refuse before any host is touched if the digest or signer differs. The host receives the verified file and needs no internet. The deploy ledger records the digest. Rollback installs the previous pin's file. Deploy, verify, rollback and promote then work as they do for an image, and a component's State, Rollback and Scope facts are declared as today ([ADR 1211](../adr/1211-rollout-preflight-readiness-and-reversibility.md)).
  - **The declaration (built).** A component with `artifact_type: release` carries `release:` with `checksums` (the release's checksums file), `files` (`amd64` and `arm64`, each one file name) and `signer` (the workflow that signs the release, `https://github.com/<owner>/<repository>/.github/workflows/<file>.yml`, with no ref: the pin's tag is its ref, so one declaration serves every pin). A release signed by a reusable workflow kept at another ref, whose certificate names that ref, is refused by this shape. Its pin, in `fleet:` and in each deviation, is one string, `<owner>/<repository>@<tag>@sha256:<digest>`, where the tag may hold a slash (`tool/v1.2.0`), the `<owner>/<repository>` is the signer's repository (compared without regard to case), and the digest is the checksums file's: it fixes every file's digest the way an image index digest fixes each platform's image, so deviations, the ledger and rollback carry one value as they do for an image. Each file name in `release:` is one path segment of `[A-Za-z0-9._+-]`, the names the `release-file` role accepts on the host. `goatbuilder pins` and `goat_consistency.resolve` refuse a declaration or pin of another shape, a pin of another repository than its signer's, and a value with a trailing newline (GB-365), in the same words, and a `release:` on any other component.
  - **Fetch and verify (built).** `crates/goatbuilder/src/release_file.rs` fetches a component's file on the operator's machine, from GitHub's release downloads or an operator's mirror directory, and refuses before anything is written (GB-381) unless: the pin's repository is the signer's repository (checked again here, before any download); the checksums file's SHA-256 is the pin's digest; its keyless signature, `<checksums>.cosign-bundle` beside it, verifies for the declared signer at the pin's tag (the same offline Sigstore checks as `goatbuilder update`, with the component's identity: `update/signature.rs`, `verify_component`); and each architecture's file is listed in the checksums file with the SHA-256 it has. The verified files are kept under the state directory by the pin's digest, and a later run verifies the kept ones again before it asks the network. `GOATBUILDER_RELEASE_MIRROR` names the mirror directory. Tested against goatbuilder's own published 0.7.3 signature taken as a component, and with a stand-in Sigstore for the whole path.
  - **Install, ledger and rollback on a host (built).** The `release-file` role copies the verified file to `/opt/goat/releases/<component>/<sha256>/<name>`, checks its SHA-256 on the host before it takes its final name, records the pin beside it, keeps the file in use as `previous` and points `current` at the new one, and writes the deploy ledger row (artifact type `release`, ref the pin). `release_file_rollback: true` switches back to `previous` with no fetch, after checking the previous file is still the one its directory names, and writes the row with that file's pin and the action `rollback`. Of the release's files, the host takes its own architecture's; a host the release has no file for is refused. Run on localhost against scratch directories (`roles/release-file/tests/local-run.sh`): install, reinstall, roll back and each refusal.
  - **Deploy, verify and rollback on both avenues (built, measured on container hosts).** `goatbuilder deploy` and `deploy-component.sh` fetch and verify before any host and before a door opens, then run the component's play: its own `deploy_playbook`, else `ops/ansible/release-file-deploy.yml`. The script calls goatbuilder's hidden `release-file` verb (`GOATBUILDER_BIN`, else `goatbuilder` on PATH), so one implementation verifies and both refuse in the same words. A dry run fetches and verifies too, prints the plan, and exits 1 when a real run would refuse. `verify` requires the ledger row and then reads the file each host's `current` names: it must be the pin's file for that host's architecture. When the release cannot be verified where `verify` runs, the host is unknown, never converged. `rollback` switches every host of one goatnet to `previous`, one step (GB-379 for more); a second rollback switches back. `ops/e2e/release-file.sh` runs all of it on a container host with goatbuilder's own published 0.7.2 and 0.7.3.
  - **Promote and fastlane (built).** `promote open` and `hotfix` take a release component at a release pin only, and an image component never at one; `promote check` refuses an open record or a set member of the wrong kind. A file has no container, so the `runtime-health` gate cannot be captured: it names that and is passed only by `--override-runtime-health` with a reason and an ack. `fastlane` verifies the release as deploy does, moves the pin, signs, lands it and deploys.
  - **Not built yet:** `release` for one (its repository releases it; goatbuilder tags nothing), a saved rollback plan (GB-379), and a run on a real host. A release that publishes no checksums file, only an attestation per file, is not covered by this pin shape. The role's `release_file_root` is the default on every host: `verify` reads `/opt/goat/releases`.
  - **A second signature format (built): the acceptance list.** Some repositories sign their checksums file as a Sigstore bundle (`<checksums>.sigstore.json`, media type `application/vnd.dev.sigstore.bundle.v0.3+json`) and not as cosign's older bundle. `release.bundle: sigstore` names it; without it, or at `cosign`, the older bundle is read. The reader is `update/sigstore_bundle.rs`. It accepts the published signature of the goat-processors runner 0.8.0, which `cosign verify-blob` also accepts. A reader of it is accepted when each of these holds and has a test (the tests carry the item numbers; item 10 is about the play and has none):
    1. **Format.** Exactly one media type is read. Any other, a duplicate key, an unknown field, a field of the wrong type (an array or null where an object must be included), text that is not UTF-8, or a bundle over the size limit is refused. No more than the limit is read. A refusal does not repeat the sender's text.
    2. **Content.** Only a message signature is read; an envelope is refused. The digest is computed from the file, and one the bundle states must equal it.
    3. **Certificate.** One leaf, held to the trusted root's CAs at the time of item 4 with the older bundle's checks (extended key usage, not a CA, critical extensions, SCT). A chain or a key in the bundle is never a trust anchor.
    4. **Time.** The log's signed entry timestamp is required and is the only time used. A timestamp authority's is not read, so it neither replaces the log's nor overrules it. No signed entry timestamp is a refusal.
    5. **Log.** The signed entry timestamp verifies, and so does the inclusion proof against a checkpoint that the same log key signed, whose origin is that log. A log whose key is Ed25519 signs no entry timestamps, so one under such a key is refused. There is exactly one entry, a `hashedrekord` 0.0.1 for this digest, this signature and this certificate. Any other type or version is refused.
    6. **Identity.** The component's identity check is the older bundle's, unchanged: issuer, repository, the pin's tag, and `release.signer`. A public key or another issuer is refused.
    7. **No downgrade.** The pins name the format (`release.bundle`). A release cannot choose, and one format is never tried after the other.
    8. **Trust root.** The embedded root, and an operator's `trusted_root.json`, as for the older bundle; nothing is fetched. A log key that two of them hold is read from both, so neither hides the other.
    9. **Fail closed.** A mutation of each field, and random corruption of the whole, is refused or leaves what is verified unchanged. A bundle that is valid for another file, tag, repository or workflow is refused. A published bundle that cosign verifies is accepted.
    10. **What it protects.** A package that runs scripts as root needs its own review of the play that installs it. The `release-file` role copies a file and installs no package.
    Not covered, each failing closed or outside the reader: a bundle from a Rekor v2 log (no signed entry timestamp, an Ed25519 checkpoint, a timestamp authority's time, newer entry types) is refused, so a publisher that moves to it stops every deploy of its component until that path is built; an operator's `trusted_root.json` adds keys and removes none, so an embedded key is withdrawn only by a new goatbuilder; the workflow that was triggered (the certificate's build config) is not compared, so a reusable `release.signer` is accepted from any workflow of that repository at the pin's tag that calls it; there is no consistency proof against a checkpoint seen before, as in any offline verification.
  - **Attestations (built): the acceptance list.** Some repositories sign no checksums file and attest each file instead, with a GitHub artifact attestation: SLSA provenance v1 in an in-toto v1 statement, in a DSSE envelope, in a Sigstore bundle v0.3 (`goat-xf-pipe-zenoh` and first-bite publish these). `release.bundle: attestation` names it. The pin is still the checksums file's SHA-256, which fixes each file's digest; each file is then verified by its own attestation, read from GitHub's attestations API by the file's SHA-256, or as `<file>.attestations.json` (the API's answer) from a mirror or an earlier run's kept files. The reader is `update/signature.rs` (`verify_attestation`) and `update/attestation.rs`, and it returns the statement it verified, so a caller can hold more of it. It accepts the published attestations of `goat-xf-pipe-zenoh` 0.1.5 and first-bite 1.1.0. Each of these holds and has a test (the tests carry `a1` to `a3`):
    1. **Format.** Items 1, 3, 4 and 5 of the list above, with a DSSE envelope in place of the message signature: exactly one envelope signature, and one log entry, a `dsse` 0.0.1; a bundle with a message signature is refused here, and one with an envelope is refused over a checksums file.
    2. **Content.** The signature is over DSSE's pre-authentication encoding of the payload and its type, so a payload is never read as another type; the entry names this payload's SHA-256 and exactly this one signature by this certificate. The envelope's hash in the entry is Rekor's own reading of the envelope and is not compared.
    3. **Identity.** Item 6, unchanged: issuer, repository, the pin's tag, and `release.signer` (the workflow that attests) at that tag.
    4. **Statement.** The payload type is in-toto's; the statement is `https://in-toto.io/Statement/v1` and its predicate `https://slsa.dev/provenance/v1`, and every other predicate is refused. Exactly one subject has the file's name, and its SHA-256 is the one computed from the file's bytes. The provenance's build type is GitHub Actions' workflow, and it names the pin's repository, `refs/tags/<tag>` and the workflow the certificate says was run (its Build Config URI: the top-level workflow, which is the SAN's own unless the signer is a reusable workflow it calls). A field it reads that is repeated or of the wrong type is refused.
    5. **Choice.** The pins choose the format, as for item 7. GitHub is asked for provenance only. Each bundle is read as the exact text sent, so its size and repeated keys are judged. Of at most 64 listed, one that does not claim SLSA provenance is passed over without its cryptography, at most 16 are checked, and the first that verifies is taken; none verifying is a refusal that counts what was refused at each check. A file or checksums file named `<name>.attestations.json` is refused by both resolvers, so no name is the attestations of another.
    Not covered: the provenance's other fields (the runner, the source commit) are not judged; which top-level workflow ran is not held to a list, as for item 6, so with a reusable signer any workflow of the repository that calls it at the tag is accepted (the code run is still the tag's); GitHub's answer is not paged past its first 30, and is read without a token (60 requests an hour from one address); a release whose attestations are only on GitHub needs the API or a mirror where it is installed from, as any release needs its files.
- **Where the service's repository publishes a deploy contract,** the play follows it and adds nothing. The goat-processors runner's contract is the model: install, self test, certificates, config check, start, doctor, acceptance replay, each with a machine-readable result.
  - **The goat-processors runner (measured).** `ops/ansible/goat-processors-runner-deploy.yml` does the contract's steps in order. The `release-file` role puts the verified package in place and records the pin; the play holds the file `current` names once more (on an install, the file goatbuilder verified; in the directory named for its SHA-256; it and the directories above it root's and writable by no one else, whatever a goatnet's group_vars say for other release components), installs it with apt at the version the pin names (older included), checks the version, runs the self test, writes the certificates, writes the config only once the runner accepts it, starts the service or restarts one that was running, requires it active, waits three ticks and two seconds, requires `doctor` to show no fail and the running service to report the package's version, then runs the acceptance replay. The package's own dependencies (adduser, systemd) come from the host's apt sources; on Ubuntu they are there. Its whole configuration is the goatnet's: `goat_processors_runner_config` (the runner's `runner.yaml` as a mapping) and, for `tls/` locators, `goat_processors_runner_tls`; with none the play stops at its first task (GB-395). `ops/e2e/runner-release.sh` runs the public row from the published releases 0.8.0 and 0.8.1 in a VM, through both drivers, with eclipse/zenoh as the router: a goatnet that did not opt in is refused, dry runs touch no host, a deploy reaches the runner's health check (`doctor`, `/v1/health`), a second deploy writes no ledger row and stays healthy, a rollback installs the package before and is healthy, `verify` names the rollback, and a previous package changed on the host is not switched to. 26 of 26 cases, amd64 with KVM. Not run: arm64, a real host, a fabric over TLS, and a certificate written by the play. Not covered: a release re-cut under the same version is not installed again (apt compares versions); `previous` can name a package that failed its health check, if one was deployed after it; and a run stopped between writing the config and the restart leaves the next run nothing to restart for.
  - **Where its declaration goes: the public table, opt-in.** `ops/pins/fleet-pins.yaml` declares `goat-processors-runner` with `opt_in: true` and the pin of runner 0.8.1, the runner's TLS fix release (environment-parity.md). A goatnet runs it only when its own row lists it under `opt_in:`, and sets `goat_processors_runner_config` for the member groups that run it; for every other goatnet it is absent, no member's `pins.yml` changes, and `deploy` and `verify` refuse it (GB-003). The row still changes the table's bytes, so every goatnet's intent `sources` hash moves and each signs again, as for any change of the table. Its file names carry the version, so a newer release moves the pin and the names together.
  - **goat-xf-pipe-zenoh (measured).** `ops/pins/fleet-pins.yaml` declares it opt-in at xf-pipe 0.1.6, `release.bundle: attestation`, its signer goat-transformers' `release-pipe.yml`. `ops/ansible/goat-xf-pipe-deploy.yml`: the `release-file` role puts the verified archive in place; the play holds it once more as the runner's play does; then, on every run, `ops/ansible/files/xf-pipe-unpack.py` judges each member (a plain file or directory under the archive's one top directory, no link), holds the tree in the directory named for its SHA-256 to the archive byte for byte and mode for mode (the play then gives the service's group read, and no one else anything), owned by root, and unpacks it again beside it and renames it into place when it is not (so a tree changed on the host, or a run stopped halfway, is put right); it points `/opt/goat/xf-pipe/current` at it, and runs it as a systemd service of its own user, with the goatnet's conversion (`goat_xf_pipe`: from_format, to_format, in, out, metrics, and an optional Zenoh configuration). Each value is one quoted argument to systemd; a value with a control character, a format that is not a pack name, and a metrics address that is not loopback or mesh are refused. The values are on the command line, which every local user can read, so a credential goes in the Zenoh configuration. Health is the service active, its metrics listener answering with `goat_xf_pipe_uptime_seconds`, and the service still active with no restart eight seconds later; when the service is not active the play prints its journal. With no conversion the play stops at its first task (GB-396). `ops/e2e/pipe-release.sh` runs the public row from the published releases 0.1.5 and 0.1.6 in a VM, through both drivers, with eclipse/zenoh as the router: a goatnet that did not opt in is refused, dry runs touch no host, a deploy reaches the health check, a second deploy writes no ledger row, a rollback runs the archive before and is healthy, `verify` names the rollback, a program changed in the unpacked tree is put back by the next deploy, and an archive changed on the host is not switched to. 29 of 29 cases, amd64 with KVM; the attestations were read from GitHub's API. Not run: arm64, a real host, a message converted end to end, and a Zenoh configuration written by the play. Not covered: unpacked trees of earlier releases are kept, one per SHA-256, and not pruned; the hold reads each path's owner, group, mode and bytes, not its ACLs, extended attributes or file capabilities; and the play makes the service's group but does not manage who is in it, so a person put in it reads the tree and the Zenoh configuration.
  - **goat-feeds (blocked).** It has no signed release, and its play takes a local binary.
- **A type lists its services** (`services:`). The machine's build deploys them, through the same code as `goatbuilder deploy`. Built: `join-node` phase 13 runs `deploy --group <group> --node <machine>` for each, so a join redeploys no neighbour and does not wait for one that is down; `deploy-component.sh` takes `--node` too. On both avenues the name must be one host of `--group` in the base inventory (`inventory/mgmt-hosts.ini`, child groups' hosts included), checked before any door opens or play runs; a group's name or a host of another group is refused (GB-003). A listed service with no component, group, pin or play is refused before any phase (GB-384), and `doctor --target` names each, reading it back with `--live`. `standup` builds a type in phase 14 the same way: after the type's plays, it runs `deploy --group <group>` for each listed service, on the type's machines at the site, and refuses one with no component, group, pin or play before any phase (GB-384); a type built in `obs-legs` lists none. No shipped type lists one yet. A dry run plans the deploy and says so. Chosen over carrying no `--ack` (the phase stopped halfway through a machine) and over passing a default (the record would name no one who accepted the risk).
- **A play that only a person can reach is a gap.** The check of gate J28 holds every deploy play to one of two answers: a verb reaches it, or a list names it with a reason. A play a verb should run and none does yet is listed as owed, with the gate row that will route it: tracked, not answered.

### 3.10 Types and services declared in an overlay

A goatnet's owner can hold a type, a service and its pins in a private overlay, with the plays and installer in a private repository. goatbuilder's code, documents, tests and releases stay the same for everyone and name none of them.

- **Where the files go.** The overlay is layered over goatcore as it is today. A type is a new file in `ops/goatbuilder/overlay/targets/`, a platform family one in `ops/goatbuilder/overlay/families/`, and a service is a component in the overlay's own pins file. The loader reads the directories, so it needs no list of names.
- **A type or component names its source as data:** repository, full commit or signed tag, the digest of what is fetched, the signer, and the paths of the play and the installer inside it.

```yaml
# overlay: ops/goatbuilder/overlay/targets/example-role.yaml (sketch; names are synthetic; the foundation's schema sets the field names)
type: example-role
families: [host-class]
encryption: root
source:
  repository: git.example.invalid/zagros/example-role
  ref: <full commit>
  artifact: {file: example-role_<arch>.tar.gz, sha256: <digest>, signer: <identity>}
plays:
  - play: example-role.yml        # inside the source repository
services: [example-service]
acceptance: {requires: [example-role]}
proof: {ci: vm, hardware: required}
```

- **A component's play (built).** A component may declare `source:` with `repository` (a git URL that holds no credential), `commit` (full) and `play`, in place of `deploy_playbook`. Both resolvers refuse another shape in the same words (GB-365). `goatbuilder deploy` and `deploy-component.sh` fetch the commit with the person's own git access into `<deploy.state_dir>/goat-sources/<component>/<commit>`, hold every file of it to the commit on each run, and run its play with goatcore's roles first, and with `-i vars-here.ini` (an inventory in `ops/ansible` that names no host), because Ansible reads `group_vars` and `host_vars` only beside the play or an inventory file. Refused before any host (GB-385): not reachable, not the commit's content, no such play, a role goatcore has, or anything Ansible would read beside a play in place of the checkout's (`group_vars`, `host_vars`, `library`, `module_utils`, `collections`, a `*_plugins` directory, in any case of letters), a link, a submodule, or anything where a role of goatcore's reads a file beside the playbook (`{{ playbook_dir }}/../enrollment/...` and the like, read from the checkout's roles): Ansible sets `playbook_dir` to the play's own directory, so for a source's play those reads land in the copy, and such a role run from a source finds nothing and fails. Its files are read from the commit's tree, an index entry marked so that git does not compare it is refused, and no git run on it takes the repository a parent git exports (`GIT_DIR` and the rest of `git rev-parse --local-env-vars`), a template for new repositories, attributes from elsewhere, replacement objects or a file-system monitor.
- **A type's own plays (built).** A type file may declare `source:` with `repository` and a full `commit`, and mark the plays in it `from: source`, each a path inside the repository. A run of `join-node` (phase 13) or `standup` (phase 14) fetches the commit the same way, into `<deploy.state_dir>/goat-type-sources/<type>/<commit>`, holds it to the commit, and finds each play there, before its first phase; the plays run with goatcore's roles first and `-i vars-here.ini`. Refused before any phase (GB-420) for the same reasons, and checked again in each play's command just before it runs, against the commit the run's plan named (a type file that pins another by then is refused). A relative `deploy.state_dir` is the checkout's, wherever goatbuilder or a phase runs; a kept copy's `.git` may hold nothing `git init` does not write, and a directory name in it is plain ASCII. The loader refuses a credential in the URL, a commit that is not 40 hexadecimal characters, a play `from: source` in a type with no `source:`, a `source:` with no play from it, and a path for a play of the tree (GB-374). A plan names the kept copy and fetches nothing. Measured with a synthetic overlay type and a synthetic repository (`tests/type_source.rs`): `join-node` phase 13 and `standup` phase 14. Not built: the `artifact` of the sketch above (a type's installer that is not a release component's). In a VM (`ops/e2e/vm/types/example-overlay.sh`): a synthetic overlay type through join-node phases 1, 2, 4, 5, 6 and 13, its play from a synthetic repository on the machine; measured on KVM amd64.
- **A signed tag (built).** Either `source:`, a component's or a type's, may name `tag` and `signer` in place of `commit`. The signer is one SSH public key (`ssh-ed25519`, `ecdsa-sha2-nistp*` or a security-key type), written as its type and base64 text. On every run, deploy, join-node and standup fetch the tag alone with the person's own access, and take it only when it carries exactly one signature, an SSH one at its end, which `ssh-keygen -Y verify` accepts for that key alone in git's namespace, and when the bytes it signs say, in git's order, one commit, that tag's name and who made it when. The commit it names is fetched and held as a commit is, in a copy named by that commit, so a run never removes a copy another run is using; a type's play takes its path from its own check when it runs, so a tag the signer moves during a run gives the later plays the newer commit. A tag made before the one an earlier run took for the same source is refused (`tag`): an older signed tag served again is not the one the signer now gives. That record (`<deploy.state_dir>/goat-source-tags/`) is one for each tag name, repository and signer, whatever component or type pins it, so two deployments that pin a tag of one name from two repositories keep two; it is judged again and written under a lock, whole, never lowered, and one that cannot be read is refused. The guard is per machine, and only a run that goes on to run the play records a tag: a dry run, `verify`, `doctor`, `history` and standup's checks judge it and record nothing. A type's phase check is held to the whole pin its plan was made with (`--pin`, a digest of repository, tag and signer), so a type file changed during a run is refused before its play. A tag that says it was made more than a day after the machine's clock is refused. The first run on a machine has no record, so it takes the tag the repository gives; a repository written another way (`ssh://` or `git@`, a trailing `.git`) or a new key starts a new record. What a signature does not say is which repository it is for: a key that signs a tag of the same name in two repositories lets one be served for the other, so a signer keeps one key per repository, or the source pins a commit. Refused before any host or phase (GB-385, GB-420): no such tag (`fetch`), a lightweight tag or another tag under the name (`tag`), no SSH signature or another key's (`signer`). Both resolvers and the type loader refuse a tag with no signer (it can move), a signer with no tag, both a tag and a commit, a tag that does not start with a letter or is a YAML word for true or false, and a key of another shape, in the same words. A person's gpg keyring plays no part. Measured on synthetic repositories (`tests/type_source.rs`, `tests/component_source.rs`, both avenues).
- **What the signature covers.** Neither `source:` is in the signed intent. The intent binds each component's artifact value for each member group; which play deploys it, `deploy_playbook` or a play in the tree, is bound by the reviewed tree that the fresh-source check (C3) holds a deploy to, and a `source:` commit names its content exactly, so it is bound the same way: the pins file, or the type file, in the reviewed tree.
- **How the source is fetched.** On the operator's machine, with that person's own access to the repository, into a scratch directory, verified against the pin. goatbuilder holds no credential for it, and nothing is cached in the assembled tree.
- **It only adds (built).** An overlay type or family whose name goatbuilder or the tree already has is refused. In an assembled tree, a file in `ops/goatbuilder/targets/` or `ops/goatbuilder/families/` that is not the marker's goatcore commit's own, or that commit plus the recorded pre-disclosure patches, is refused. So a public type's meaning cannot change in one goatnet. An overlay type passes the same schema, `doctor --target` base check and proof tiers as a public one. Measured through the binary (`tests/overlay_adds_only.rs`), and the recorded plans of every public type (`tests/target_type_plans_unchanged.rs`) are the same bytes with a synthetic overlay beside them.
- **Refusals, each with its own error code:** the source is not reachable with this person's access; the ref is a branch or an unsigned tag; the digest or signer differs; the type name is taken; a listed service has no component. The catalog's text carries no type name; the name is a value filled in at run time.
- **Nothing leaves with it.** Run records, the ledger and acceptance results of an overlay type are written where the goatnet's own are written. Shell completion, `tutor` and the generated reference list only the types in the tree they run in, and the released reference is generated from a public tree.
- **Proof.** Public CI proves the mechanism with a synthetic type and a synthetic repository. The owner's repository runs the CI tier for its own type, by calling the public harness as a reusable workflow with a published goatbuilder.

## 4. The order of work

One revertible pull request per step, on the program's normal path. No dates. **One foundation first, then five lanes that run in parallel.** The only dependencies are real ones: nothing moves onto type files before the files and their reader exist, and nothing on a small computer is built or proven before the small-computer builder exists.

| Part | Work | Waits for |
|---|---|---|
| Foundation | the type and family file formats and their reader; `doctor --target`'s base check; the CI VM harness | nothing |
| Host-site lane | core and obs onto type files; standup phase 11 automated | foundation |
| Boundary lane | federation boundary and simple boundary as types | foundation; their small-computer variants also wait for the small-computer builder |
| Processing lane | goat-processors as a type | foundation |
| Small-computer lane | the small-computer builder brought in; then break-glass, network-gear jump box, Billie node, octo-pod, vendor gateway, first-bite, network tap | foundation |
| Services lane | the `release` artifact type; the services that need it; the deploy-play check; overlay declarations; a type's services list | overlay declarations and services lists wait for the foundation; the rest waits for nothing |

### 4.1 Foundation

Built one type at a time: the formats and core first, proven unchanged against today's plans, then each other type.

**What the foundation holds.**
   - The type and family schemas and `ops/goatbuilder/targets/`, with core, obs, break-glass and network jump box moved onto them. `join-node` and `standup` read the files, and the compiled list at `joinnode.rs:90` goes. Built: the formats and their reader (`crates/goatbuilder/src/targets.rs`), the five type files, and the plans of every type recorded and unchanged (`crates/goatbuilder/tests/target_type_plans_unchanged.rs`); the compiled list is gone.
   - Acceptance rows for breakglass and network-jump, which have none today.
   - `doctor --target` for these four types.
   - The CI tier's VM harness, for the first type that uses it.
   - **A pure refactor.** `join-node` and `standup` print the same plans before and after: the golden plans (`crates/goatbuilder/tests/full_plans_unchanged.rs`) stay byte-identical, and a per-type `join-node --dry-run` parity test is written first.
   - **Phase entries are of three kinds:** a play, run as today; a built-in step whose logic stays in Rust behind a name (a core joiner's seeding, replication wiring and certificates); or a declared skip with its reason.
   - **A play may live outside goatcore.** The type file names its source repository as data, and the loader does not require the play, so a public clone loads every type. At run time a missing play is refused with its own error code, naming what to assemble. The network-jump play is the first such case, and the edge kinds' installers follow the same rule.
   - **Models stay in `ops/bootstrap/hardware-classes.yaml`** for step 1, grouped into families, and gain what each delivers. Its roles axis is marked superseded by the type files; it is deleted in a later step, once first-boot role selection stops reading it.

   Follow-ups, each its own pull request (Designed):
   - A type's required inputs refused before the node is changed: for network-jump, `herd_connector_image`, which was only named in a label. **Built:** a type file's `inputs` (`ops/goatbuilder/targets/README.md`); a machine without one, or with the role's placeholder (`PENDING`), is refused before any phase (GB-414) by `join-node` and by a `standup` run that reaches phase 14, and `doctor --target` shows each as a row. It changes `join-node`'s plan for network-jump (the label, and the `declared` row), so its recorded plan is updated.
   - The roles axis of `hardware-classes.yaml` deleted, once first-boot role selection reads the type files.
**Standup phase 11, automated (host-site lane).** This removes the two manual steps at `standup.rs:630` and `standup.rs:636`.
   - **Today**, the operator does four things by hand. First, the first dashboard login with the bootstrap password (`goatnet-standup.md:545`). Second, a re-run of `dashboard-deploy.yml`, whose post-task promotes the first user (`dashboard-deploy.yml:212`). Third, the admin service user `svc-<site>-netbird-infra` and its token, made in the UI. Fourth, storing the token as `<SITE>_NB_API_TOKEN` and resuming at phase 12, which mints every other identity from it (`standup.rs:647`). It is manual because the first NetBird admin needs an interactive sign-in (`goatbuilder-speed.md:152`).
   - **The route ([ADR 1274](../adr/1274-standup-mints-the-bootstrap-netbird-token-through-the-management-image.md), Proposed):** the fleet management image's own command, `service-user` in `ops/netbird/patches/service-user-token-bootstrap.patch`, fixed. The image already carries that patch, a recorded [ADR 1248](../adr/1248-goat-follows-stock-upstream-netbird-and-wireguard-and-retires-its-departures.md) departure, so this route needs no new departure; an earlier version of this section chose a raw-SQL verb in `ops/mgmt-host-bootstrap` on the premise that it did, and ADR 1274 replaces that route. Two steps, each a one-shot container of the pinned image with only the host's tmpfs directory `/run/goat-bootstrap` (root, 0700) mounted. The first creates the admin service user through NetBird's store code and makes the token with NetBird's code: it writes the plaintext once, to an `O_EXCL` mode-0600 file, keeps the token row (hash only) beside it, and saves no token row in the database. The operator side pipes that file into the declared secrets store and reads it back (value stores through `posture.py`; 1Password as phase 12's `--mint` writes it; openbao, vaultwarden, custom and `env` are refused, and phase 11 stays manual there). It pipes the read-back value to the second step, which refuses unless it equals the pending plaintext, then saves the token row. Both steps write NetBird's activity events, and a step whose event fails fails. Phase 11 becomes those applied steps plus the existing `--live` gate, only where `goatnet_founder: true` is declared, and the first human login moves after the standup.
   - **Its checks:**
     - the account and its owner exist;
     - it reads state: a service user that holds its token, with a stored copy that authenticates, is left as it is; one with no token row resumes; one with a token row and no stored copy is refused; a token already stored is never replaced by a standup. Renewal and that recovery are one deliberate rotation (ADR 1274): a new pending token; the old value kept in the same posture as `<NAME>_PREVIOUS`; the stored copy replaced and read back in every place the posture keeps it; the new row saved while the old still works; the new token checked; then, on a person's confirmation that each consumer has the new value (the ones deployed from goatstuff cannot be checked here), the old row deleted and `<NAME>_PREVIOUS` removed;
     - the token authenticates;
     - the store is writable;
     - the management version matches the pinned image.
   - **Its refusals:** a version mismatch; a service user with no stored token; management unreachable; the store not writable; the `--live` authentication failing.
   - **Its CI-tier proof:** a founder standup through phase 13 with no MANUAL row. Then the service user and token are checked through the API, the token appears in no log, a re-run mints nothing, and each refusal case is exercised.
   - **Status:** Designed. It mints an admin credential for the mesh control plane, so its build is reviewed as a trust change before it starts.

### 4.4 Processing lane

- **goat-processors as a type**, host-class only. Its plays install the engines from the public `goat-processors` repository at a pinned release. Its acceptance runs them on recorded data and checks the output against the repository's conformance vectors.
  - **Built in part.** `ops/goatbuilder/targets/goat-processors.yaml` is the type: host-class only, no other family. `join-node --class goat-processors` builds the machine by push, and its phase 13 names the release component `goat-processors-runner`, as the network tap names goatrope (section 3.9): where the pins have a release pin of it for the machine's group (it is opt-in, so only a goatnet that lists it), phase 3 runs `goatbuilder deploy --dry-run` for it and phase 13 runs its play, the row's `deploy_playbook`; where they have none, phase 13 is a declared skip and the machine runs no engine. The component and its play are the runner's (section 4.6, step 2, gate J24): the play follows the runner's deploy contract (`runner/DEPLOY-CONTRACT.md` in the engines' repository: verify, install, self test, certificates, config check, start, doctor, acceptance replay), and the type file adds nothing to it. **Measured in a VM** (`ops/e2e/vm/types/goat-processors.sh`, amd64): the public row, opted in by the synthetic goatnet, installs runner 0.8.1 from its published release, verified against its Sigstore bundle on the operator's machine; then the type's acceptance: the conformance vectors the package carries (121 under `packs/*/vectors/`) are byte for byte the repository's at the release's own commit (`runner-v0.8.1` is `4a7ed49b6873b31de0145ebbaac421a24bd91b56`), fetched from that commit, and the installed runner reproduces every one (`goat-processors selftest`: 121 of 121, none failed). A second phase 13 passes. The runner's fabric router there is eclipse/zenoh in a container on the VM's host. Not built: an arm64 run, and a runner on a goatnet's own fabric with its certificates.

### 4.5 Small-computer lane

1. **The small-computer builder brought in.** `goatbuilder image <model>` wraps the Pi base-image builder for the Pi model; its steps that need a person (the card, the console during encryption, the YubiKey) stay as directions with the end state checked. The other two Pi preparations fold into it. The OnLogic model joins when the hardware is in hand.
2. **Then, in any order:**
   - break-glass and network-gear jump box moved onto the small-computer family (ADR 1114 §5's checks with them);
   - Billie node, per section 3.4, once the platform has a signed release and signed relay bundles;
   - octo-pod, push-deployed: `join-node` reaches it and pushes, like any other type; the pull converger comes after 1.0 (gate group D) and arrives as a value of `converger:` without changing any type file;
   - vendor gateway, installing the vendor bridges at a pinned release (ADR 1255);
   - first-bite, installing it at a pinned release;
   - network tap (section 3.8): the Raspberry Pi's inline mode first, as it is built and measured; listen mode beside it; better fail-open hardware later.

### 4.6 Services lane

1. **The `release` artifact type** in the pins schema and both drivers (gate J23). Built: declared, fetched, verified, installed, verified on the host, rolled back, promoted and fastlaned, measured on container hosts. Next: a run on a real host.
2. **The goat-processors runner, then `goat-xf-pipe-zenoh`, then goat-feeds** as components (J24). The runner is first because its deploy contract is written. goat-feeds waits for goatstuff to publish a signed release of it.
3. **goat-map's pins row** (J25), beside step 1: it is an image.
4. **The deploy-play check** (J28), beside step 1, first as a report: it names today's gaps. Each gap then gets a component, a phase or a listed reason, and the check becomes blocking. Built: the check, blocking in CI for goatcore (`ops/ci/check-deploy-plays-reached.py --strict`, run by `.github/workflows/deploy-play-reach.yml`). Of the 22 gaps section 2.4 lists, 4 are listed under `unreached:` with a reason (a reason that names a play must name one a verb reaches), and 18 under `owed:`, each naming the gate row that will route it, so strict holds new plays while those 18 stay counted. It reads the other public repositories' deploy plays too, each at the full commit the list pins (`repositories:`; CI fetches them, and reads them as YAML only): goatstuff's and goatrodeo's unrouted plays are owed, goat-map to J25, goat-feeds to J24, the rest to J28. Not built: a route for the owed plays; a new play in another repository is seen only when its commit is bumped in the list.
5. **After the foundation:** overlay types and services (J26), and a type's services list (J27).

### 4.7 Fieldkit tools a type serves

A Fieldkit tool is a single-file page a host serves over its own API ([fieldkit-and-bleating-edge.md](fieldkit-and-bleating-edge.md)). A type file lists the Fieldkit tools its machine serves, and the type's acceptance checks each one is served and passes its scope guard. The first is Fieldkit Gatepost, served by the pod API (`ops/goat-pod-api`, ADR 1251) on a machine that runs it, such as an octo-pod. Operator-facing pages goatbuilder itself adds use the Bleating Edge design system.

## 5. What does not change

- The node classes, their ACL positions and their enrolment rules stay as ADRs 1114 and 1131 set them. A break-glass node's enrolment stays manual, by ADR 1114's reasoning.
- A site still declares which rescue machines it has, or why it has none (ADR 1183).
- Roles, not hardware (ADR 1141): a target type names a role. A family names hardware, and a model joins it.
- Each edge kind's repository keeps its own installer and owners; goatbuilder calls it at a pinned release.

## 6. Open questions for the operator

1. **How the sensor kit is installed.** Decided by the operator (23 Nov): "support both methods goatbuilder and the billie method for billie". goatbuilder installs the kids on the public platform's model (section 3.4), once it has a signed release and signed relay bundles, and the `billie` commands stay supported on their own. Where kids may run besides Billie nodes is question 3.
2. **Fabric client certificates.** Decided by the operator (23 Nov): the site's own certificate authority issues them for Billie nodes.
3. **Relays on other types.** Do any types besides the Billie node run sensor relays, given that the kit's platform brings its own local router and container runtime?
4. **The Pi's OS baseline.** Decided by the operator (23 Nov): "support both", Ubuntu Server 24.04 and 26.04. What each Billie part supports today is in section 3.4; the public platform is 24.04 only.
5. **The tap's repository.** Decided by the operator (23 Nov), for a public repository of its own, usable without goat: "tap is not goat core, lets do this". Named `goatrope` (operator, 23 Nov: "let's go with goatrope for the name"). It also covers decode-and-send and a relay role, which transmits on the link (section 3.8). Open: its owner, set by that repository's own ADR.
6. **The fail-open part.** Decided by the operator (23 Nov): not standardized now; the Raspberry Pi setup is supported as it is, and the tap's hardware is improved later. Candidates: a passive copper tap (100 Mb/s), a powered tap device that closes the link when its power fails, a mirror port on the site's switch. Gate J22 measures a listen-mode source.
