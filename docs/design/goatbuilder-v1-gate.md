## What this is

`goatbuilder` 1.0 is the first release that carries a promise: a deployment
that works on 1.0 keeps working on every later 1.x release without a change
to its files or to the programs that call the binary. Releases before 1.0
carry no such promise.

A build is tagged 1.0 when every requirement in "The gate" has passed its
test. Each requirement names one test, so that "ready for 1.0" is a result
a person can read and not an opinion. Nothing is added to the gate, and
nothing is removed from it, except by a change to this file.

## What 1.0 promises

Four surfaces are what other people build on. From 1.0, each one changes
only by the rule beside it.

| Surface | Where it is defined | Rule from 1.0 |
|---|---|---|
| The configuration: `goatbuilder.yaml` and the peering declaration inside it | `ops/goatbuilder/schema/goatbuilder-v1.schema.json` | A file that validates on 1.0 validates on every 1.x and means the same thing. New fields are optional and their absence means the 1.0 behavior |
| Commands, flags and exit codes | [command reference](../reference/goatbuilder/command-reference.md); [the contract, "Exit codes"](../reference/goatbuilder/06-contract.md) | No command or flag is removed or changes meaning in 1.x. Exit codes 0 to 4 keep their meaning |
| The `-o json` and `-o yaml` documents | [goatbuilder-output.md](goatbuilder-output.md) | Each document carries its version. Fields are added, never removed or retyped, within one version |
| Error codes `GB-nnn` | `ops/errors/catalog.yaml` | A code is never reused for a different fault. A retired code stays in the catalog, marked retired |

**Deprecation.** A command, flag or field that is to be removed keeps
working, with a warning that names its replacement, for at least two minor
releases and at least 90 days from the release that first warns, whichever is
later, and is removed only in the next major version. The operator chose this
period on 2026-11-13 ([ADR 1228](../adr/1228-goatbuilder-keeps-its-four-surfaces-and-removes-only-in-a-major-release.md),
"The deprecation period").

**Updating.** An installed 1.x updates to every later 1.x release with a plain
`goatbuilder update`. The binary trusts a compiled-in list of release signers
(`RELEASE_SIGNERS` in `crates/goatbuilder/src/update.rs`), with a checkout's
`repo.release_source` (else `repo.source`) trusted beside them, never
instead of them; its own build provenance is never a signer. A signer change ships first in a release
that trusts the old signer and the new one, signed by the old; only a later
release is signed by the new one alone
([ADR 1252](../adr/1252-goatbuilder-trusts-a-declared-list-of-release-signers-and-a-signer-change-overlaps.md),
"The overlap rule"). Built: the list and the addition, with unit and
integration tests (`crates/goatbuilder/tests/update.rs`). Not built: the
release gate that runs each supported install's `update` against a candidate
(row E3).

**What 1.0 does not promise.** The text of tables printed for a person. The
shell scripts beside the binary, which stay documented and unsupported
([ADR 1201](../adr/1201-two-avenues-scripts-documented-cli-supported.md)).
The internals of a converger. The `goat` client, which has its own releases.

## The gate

Status words: **built** (the code is on `main`), **designed** (decided, not
implemented), **not built**, **in review** (a pull request is open),
**measured** (a named run with a record passed), **not measured** (exists and has not been exercised by the named test).

### J. Every machine kind is a build target

- **platform families**, which hold hardware and its preparation (the golden path lives there; a model joins a family);
- **target types**, a machine's role with its plays and acceptance, read by `standup`, `join-node` and the image tooling.

A service is software placed on a machine that already exists. It is not a type: `goatbuilder deploy` puts it there, as a component of `ops/pins/fleet-pins.yaml`. The services lane closes the gaps in that coverage ([goatbuilder-build-targets.md](goatbuilder-build-targets.md) §2.4).

A Billie node runs the sensor kit's relays for the sensors declared on it. Each site's network gear (its switches and routers) is not built by goatbuilder: it is reached only through the network-gear jump box, and every machine depends on it.

goatbuilder builds from a reachable Ubuntu host with an SSH key. `goatbuilder doctor --target <type>` checks the end state whichever path installed the machine. Each type passes the CI tier: a VM from a fresh cloud image, through the build, to its acceptance and `doctor --target`, extending [ADR 1200](../adr/1200-deployment-e2e-three-tiers.md). For the small-computer family, an arm64 VM proves the software, and the builder's physical steps are proven on the bench. The hardware tier, a recorded run on real equipment, is required only where there is equipment.

**Order: one foundation, then five lanes in parallel.** Every lane waits for the foundation, except that the services lane's J23, J24, J25 and J28 wait for nothing. Inside a lane there is one dependency: the small-computer types wait for the small-computer builder (J12). In the services lane, J24 uses the artifact type of J23. The exact 1.0 cut line of each row is not set row by row. This group was added at the operator's direction (19 Nov, extended 22 and 23 Nov); the operator accepted ADR 1257 on 26 Nov and had the lanes run in parallel.

## Order of work

The requirements depend on one another in this order. No dates are set here.

1. **0.5.0.** B1 and B7.
2. **Federation completed.** B2 to B6 and B10, each its own release in the 0.x line, each behind a switch until its scenario passes.
3. **Federation on standing goatnets.** B9. B8 no longer waits for it: the operator accepted ADR 1225 (15 Nov).
4. **Real machines.** C3, then C1 and C2 on hardware.
5. **The tool shows its work.** F1 to F6, in 0.x releases, beside the steps above.
   **A node on a phone.** H1, H2 and H6 first, because they are faults on every new node; then H3 to H5.
   **A joined site runs cut off.** I3 beside H1 and H2, in `join-node`. I1, I2 and I6 before I4; I4 before I5.
   **Every machine kind is a build target.** J as [goatbuilder-build-targets.md](goatbuilder-build-targets.md) §4 orders it: the foundation (J1), with the phone's type file beside it (J2); then five lanes in parallel. The host-site lane is core, obs and standup phase 11 (J3 to J7); the boundary lane, federation and simple boundary (J8 to J10); the processing lane, goat-processors (J11); the small-computer lane, the builder (J12) and then break-glass, network-gear jump box, Billie node, octo-pod, vendor gateway, first-bite and network tap (J13 to J22); the services lane, release files as components (J23), then the services that need them (J24), with J25 and J28 beside, and overlay declarations and type service lists (J26, J27) after the foundation. The hardware rows (J4, J6, J9, J14, J16, J22) go with C1 and C2.
6. **The promise.** A1 to A5, and the items the pull decision in D leaves before 1.0 (push behind the converger trait; per-machine pending and unknown in the `-o json` documents is built, #1095). From this point the surfaces are frozen.
7. **Upgrade tests.** E1 to E3, against the release that froze the surfaces.
8. **The cold-read drill.** C4 and C5, on a release candidate `goatbuilder/v1.0.0-rc.N`.
9. **1.0.** Every row of the gate reads "passed", with a link to its test run or measurement.
