## 1. What rotation means for a peering

A peering between two sovereigns uses eight kinds of key and certificate on our side, and the partner has its own. Two of ours, the peering leaves and the forwarder carrier keys, can be replaced without the partner doing anything, and SPIRE's CA rotates itself. The others are bound into what the partner holds, so replacing one is a two-party act. The design below gives each key one rotation procedure, run by one command, and says which phases run again, what the partner must do, and whether data keeps flowing while the two sides are out of step.

Throughout, "the command" is `goatbuilder federate <partner>`, whose fourteen phases are defined in `crates/goatbuilder/src/federate/mod.rs:303-361`: 1 preflight, 2 prepare (interface, keys and SPIRE bundle), 3 `init` (our package), 4 `lint`, 5 the exchange and confirmation 1, 6 `compose`, 7 `verify`, 8 mint the peering leaves, 9 `apply`, 10 admission on our core, 11 the transport, 12 the edge router and the outbound republisher, 13 SPIRE federation, 14 acceptance.

A resumed run skips a phase only when the phase is skippable, its journal record says it passed, and its recorded input and output digests still match; the first phase that must run again ends all later skipping (`crates/goatbuilder/src/federate/run.rs:412-419`). Only the MANUAL phases (5, 10) and phases 3, 6 and 9 are skippable (`run.rs:205-207`). Every other phase always runs. Rotation therefore needs to change the right digest, and the rest of the run follows from the journal.

### What `--rotate` does

`peering_leaf_material.py --rotate` (`ops/federation/standup/peering_leaf_material.py:263-405`) replaces every leaf pair named with `--leaf`, and only those; `mint-peering-leaves.sh --rotate` passes it through (`mint-peering-leaves.sh:62`, `:220`). Without `--rotate`, a missing pair is issued, a valid pair is reused, and a pair that fails validation (including one valid for less than `--min-valid-seconds`, default 86400, `:270`) is refused with "inspect it before using --rotate". With it, every named pair is issued again. The steps are:

1. It takes a non-blocking `flock` on `<out>/.mint.lock` and refuses if another run holds it (`:299`).
2. A `<out>/.rotation-pending` that is a file (an earlier release's journal) is refused for an operator to inspect (`:303-305`). A `.rotation-pending` directory is a committed rotation a killed run left: the run finishes it first (`finish_rotation`, `:229-260`), mints nothing more in this run, and goes on as a plain run (`:310-316`).
3. Because something is to be issued, it needs our CA key, and it checks that the key matches the CA certificate (`:340-346`).
4. It mints every pair into `new/` of a private (0700) staging directory `<out>/.mint-*` and validates each one before touching a target (`:351-358`).
5. When pairs already exist, it copies them into `previous/` beside it at mode 0600, writes `journal.json` naming the leaves with their names and addresses, and syncs both (`:359-371`).
6. **The commit:** it renames the staging directory to `<out>/.rotation-pending` (`:373`). Before this step a killed run leaves only staging, which the next run removes; after it, the next run finishes the rotation.
7. `finish_rotation` moves each new file still in `new/` over its target with `os.replace`, validates every rotated pair, and removes `.rotation-pending` with the previous pairs in it (`:229-260`). If a move fails or a pair does not validate, it copies the previous pairs back at their own modes (`restore_previous`, `:212-226`), removes the directory, and refuses. Then it places `our-ca.pem` if its content differs (`place_our_ca`, `:162`).

So a rotation either completes or is rolled back, the previous pairs are kept only while it is under way, and no run mints a third pair. `ops/federation/standup/test_peering_leaf_material_interrupted.py` measures it with real OpenSSL: a run killed while minting leaves the old pairs in place, and a run ended abruptly while installing is finished by the next run (with or without `--rotate`) from the pair it had minted, or, with that pair damaged, rolled back to the old pairs. New leaves are valid for `--days`, default 90 (`peering_leaf_material.py:269`, `FED_LEAF_DAYS` in `mint-peering-leaves.sh:56`).

## 3. Each key: what rotation does

For every key the procedure has the same shape:

1. Set the old material aside, never delete it.
2. Make the new material.
3. Run the command again from the first phase whose input changed.
4. Stop at the human confirmations the key requires.
5. End with phase 14.

The table gives the parts that differ. "Gap" means a window in which data does not flow.

### Retiring the old material

Rotation in this design replaces material; it does not revoke it. A replaced leaf keeps the same name and the same trusted CA, and nothing on the path checks a CRL or OCSP (`roles/goat-peering-edge/defaults/main.yml:140-158` states this for the fabric's access layer), so the old leaf still authenticates until its `notAfter`. A leaked leaf key therefore stays usable for the rest of its validity, 90 days by default. The fabric leaves are issued by the site CA, which every peering and every service shares, so no step retires one peering's old leaf early. A shorter `FED_LEAF_DAYS` shortens the window. The IPsec transport differs: its partner CA file is per peering, so rotating that CA retires exactly that partner's leaf (same lines). For WireGuard, the old key is retired the moment the partner's phase 11 runs, because each interface holds exactly one peer.

## 4. The CA overlap

Rotating our CA (K2) cannot keep data flowing with today's checks, because every check accepts exactly one CA per party. The design makes the agreement name a party's next CA during a rotation, and makes each check accept exactly the set the agreement names. The cutover then becomes three steps in which data keeps flowing:

1. **Announce.** Our package carries `ca_fingerprint` and `ca_fingerprint_next`. Both values are read aloud at confirmation 1. The partner composes, and admission and the edge role place both certificates in `partner-ca.pem`. The partner now trusts both CAs for us. Our own `our-ca.pem` holds both as well.
2. **Switch.** Phase 8 `--rotate` re-issues our leaves under the new CA, and phases 10 and 12 install them. Both sides already trust the new CA, so data keeps flowing; the only gap is the edge restart (as for K3).
3. **Retire.** Our package drops the old fingerprint, and `ca_fingerprint_next` becomes `ca_fingerprint`. A new agreement is composed, and each side's checks remove the old CA. Every leaf of the old CA stops being accepted at that moment.

This changes the package specification (§5.1 binds one fingerprint per party) and the agreement schema, so it needs an ADR that supersedes those lines before it is built: [ADR 1242](../adr/1242-a-partys-next-ca-is-announced-in-package-v2-so-its-ca-rotates-without-a-gap.md) (Accepted) carries the next CA in package v2, keeps v1 unchanged, and makes a v1 peering's CA rotation a gap rotation. That ADR also settles version skew, the normal case between two sovereigns. A reader on an older goatcore reads only the members it requires (`parse_package`, `crates/goat-federation/src/package.rs:137-230`), so an optional v1 member would be ignored, the reader would keep trusting only the old CA, and the switch would cut it off. Carried in v2 instead, the announcement reaches only a partner that composes v2; a v1-only partner refuses the package at composition step 1 by name, and the peering keeps the gap rotation. A CA that may be compromised is never overlapped (ADR 1242 decision 7). Rotating the site root affects every service under the site CA, not only federation ([internal-tls-ca.md](internal-tls-ca.md) lines 365-366 name the larger ceremony). The federation part designed here is the follow-through on a site CA rotation that has already happened.

## 5. The command

A rotation is one command with one decision: which key. This follows [ADR 1225](../adr/1225-federation-belongs-to-goatbuilder-one-command-one-decision.md) decision 2 (one command, one decision) and keeps its two human confirmations (decision 3) exactly where a key requires them.

```text
goatbuilder federate rotate <partner> <key>      key: leaves | carrier | transport | ipsec-leaf | ipsec-ca | signing | ca
```

`ca` is refused until the overlap of §4 is built. `rotate` is a subcommand, like `backout` (`crates/goatbuilder/src/federate/plan.rs`, `Stage::Rotate`; dispatched at `crates/goatbuilder/src/main.rs:1784-1793`). This build rotates `leaves`, `carrier` and `transport`, and on an ipsec-fips peering `ipsec-leaf` and `ipsec-ca` (§8). A key it does not rotate is refused before anything runs: `signing` with GB-189, naming what is missing, and `ca` with GB-282 (`rotation.rs`, `KEYS` and `refused`). For the named key it:

1. **Takes the peering's lock** (`<work>/.lock`, held by every run, GB-180). For `leaves`, an unfinished rotation is the leaf helper's `.rotation-pending`, which the next phase 8 finishes or rolls back (§2).
2. **Sets the old material aside** in a private directory beside it. For `leaves` this is the helper's own `--rotate`, whose copy of the old pairs (0600) is removed when the rotation commits. For `transport` and `carrier` it moves the key files on the edge (and on the forwarder) aside, so the `creates:` guards in phase 2 make new ones.
3. **Records the rotation in the run journal**, so the first changed digest starts the run at the right phase. It writes `<work>/rotation.json` (the key and a nonce), which phase 3 reads as an input when the file exists. Today phase 3's inputs are only the signing key (`run.rs:172`), so a new WireGuard key would let a resumed phase 3 be skipped and leave a stale package. The record is read only when present, so a journal written before it existed keeps its digest and an upgrade reruns nothing; the measured public key itself cannot be an input, because it is known only by measuring the edge, which is phase 3. The CA certificate joins the inputs with the CA overlap (§4), the only rotation that changes it.
4. **Runs the command again from there.** It stops only at the confirmations the key requires:
   - **Confirmation 1** for `signing`, `ca` and `transport`: the partner needs a new package. For `transport` it is a package delivery, not a re-binding.
   - **Admission** for `leaves` and `ca`: the core's leaf changes. The approval digest covers the staged files, so an old approval does not carry over (`admit.rs:820-833`).
5. **Ends with phase 14.** It prints which side still has to act, with the partner's exact command.

The partner side needs no new verb. A partner answering our rotation runs the ordinary command. For `signing` or `ca` it passes the new value with `--partner-key` or `--partner-ca-fingerprint`, which already makes phase 5 and everything after it run again (`run.rs:405-411`).

For `transport` the partner runs `goatbuilder federate <partner> --from 5`. A resumed run would skip phase 5, whose inputs (our package, the partner's package on disk and the partner's CA) have not changed (`run.rs:174`, `run.rs:205-207`), and `--from` turns skipping off (`run.rs:277-285`). Their phase 5 must then receive our new package. It verifies under the key they already hold, so a signature cannot tell it from an older one; and the agreement digest does not change, because the transport key is not in the agreement (`federation-package-spec.md:1113-1116`), so confirmation 2 does not stop either. The confirmation below is what receives it: `goatbuilder federate <partner> --from 5 --partner-key <key> --partner-ca-fingerprint <fp> --accept-partner-package <digest>`.

**Built; the decision is accepted** ([ADR 1229](../adr/1229-a-partners-new-package-is-confirmed-within-confirmation-1.md), amending [ADR 1225](../adr/1225-federation-belongs-to-goatbuilder-one-command-one-decision.md) decision 3): **a partner's new package under the same key is confirmed within confirmation 1.** When the directory, or the hand exchange, offers a package that verifies under the bound key and differs from the one on disk, phase 5 shows which members changed (for a transport rotation, `transport_offer.public_key`) and the new package's digest. The two sides read that digest aloud on the call, as confirmation 1 already does for keys, and a person confirms it (`yes` at the terminal, or `--accept-partner-package <digest>`). Only then is the old package copied to `<work>/theirs.canonical.json.previous-<UTC time>` and the new one renamed over it, so the place holds the old package or the new one at every moment, a crash included; the copy aside (with its folder entry) and the new file are synced to disk before the rename, and the folder after it. A copy aside that cannot be synced is removed and nothing is placed. A failure before the rename removes the copy aside and leaves the old package in place, and says so (GB-184). A failure after it (the folder sync) keeps the copy aside and says which state it left: the new package is in place but not recorded as confirmed, and the old one is at the copy (GB-184); run phase 5 again, and it asks again about the held incoming package, the one now in place. On the hand path, where nothing is kept aside, a failure after the rename says the package confirmed is in place but not recorded, and one before it that the file there is as it was. A package missing from the place after it was confirmed is named as such (GB-191, "no package held at …; run phase 5 again with them"), not as a folder that cannot be written. Without the confirmation the run stops and names the digest (GB-192's family, as for a package held back from their pointer, `confirm.rs:491-609`), and `--yes` never confirms it. It is journaled with confirmation 1, bound to the digest. Placing a package because it verifies was rejected: a package's `issued` is a date only (`federation-package-spec.md`, line 50), so two packages of one day are not ordered, and a directory could replay an older one.

How it is built (`crates/goatbuilder/src/federate/confirm.rs`, `incoming`; `ops/federation/standup/directory.py`, `offer_new_package`):

- **Where a new package waits.** The directory step, with `--per-counterparty` (goatbuilder's default) and the partner's key in the keyring, saves a package that verifies under that key and differs from `<work>/theirs.canonical.json` at `<work>/theirs.incoming.json`, says which members changed and its digest, and places nothing. This holds for a package from their slot for us and for one through their single pointer; for the second it also writes `theirs.incoming.json.pointer`, and phase 5's question then says the package came through their pointer and may be the package of another of their peerings. On the hand-exchange path (`FED_NO_DIRECTORY=1`) a person leaves the new file at the same `theirs.incoming.json`.
- **A copy over the placed file.** The keys confirmation records the digest of the package it was given for (`partner_package`), and its `issued` date when it can be read. A package on disk that is not the last one confirmed is asked about the same way; the package it replaced is not known, so nothing is kept aside. Once confirmed, the bytes confirmed are written to the place again, so a file copied over it while the person was asked is not what composes.
- **A peering confirmed before this build.** Its journal records no package. On its first run under this build, before any phase, the package held now is recorded as the confirmed one: journaled as `partner-package-recorded` with `how: migration`, a record the build makes, not a person's confirmation. From then on it gets the same refusals and the same compose check as a new peering. A held package that cannot be read stops the run with GB-310, exit 1.
- **An older package is refused, never asked about.** A package's `issued` date is the only member that orders a party's packages. One issued after the package held, or on the same day with a different digest, is asked about; for the same day the stop shows both digests, since nothing in the two packages orders them. The same package is no question. One issued before it fails with GB-308, even with `--accept-partner-package` and its own digest, and is set aside: asking again would turn a replay into a rollback approved by habit. One the parser refuses, an `issued` that is not a date among others, fails with GB-191 as not well formed, and so does one whose `issued` is more than 7 days after our UTC date: confirmed, a date that far ahead would make every honest later package read as older and lock the peering. The bound still leaves a window: the partner, or anyone holding its signing key, can sign a package dated up to 7 days ahead, and once that package is confirmed the partner's honest packages read as older (GB-308) until its date passes. A package without a readable `issued` cannot be ordered against a known date, so it is refused too. When the held package's date is not known (a migrated record of a package without one), a newer package is asked about, and the stop says `order unknown: the package held has no readable issued date`; an empty date is never journaled. A partner that rolls back on purpose publishes the package again with a later `issued`. The directory step does not offer an older package at all. On the hand path the keys confirmation records the held package's `issued` (`partner_package_issued`), so a copy over the placed file is compared the same way.
- **What is refused.** A package offered as new that is not signed by the bound key, or not from the same sovereign id, fails with GB-191 and is set aside as `theirs.incoming.json.refused-<UTC time>`, so the next run does not ask again. A digest given by flag that is not the new package's fails with GB-191. A package offered that is the one on disk is no question, and the saved copy is removed.
- **What is recorded.** The confirmation is journaled as `partner-package` at phase 5, bound to the digest, with the digest it replaced and the members that changed. The step runs before the keys are bound, so the keys confirmation that follows is bound to the new package, and compose is planned again from it.
- **The keys are not asked again when they are unchanged.** After the new package is confirmed and placed, phase 5 ends there when the last keys confirmation still names the key the keyring binds, the CA fingerprint the new package carries (and their CA certificate on disk is exactly that one), and our own key and CA fingerprint, the keys compared exactly and the fingerprints as hex; the phases after 5 are planned again from the new package, so a transport rotation runs on through compose with only `--accept-partner-package <digest>`. Phase 6 then does not ask the agreement digest again when the recomposed agreement's digest is the one confirmed with the partner before, which it is after a transport rotation, since the agreement carries no WireGuard key (K4 above); a changed digest is asked as before.
- **Our own transport rotation does not stop at phase 5.** After `rotate <partner> transport` only our package has changed (the new WireGuard key). When the last keys confirmation still holds on both sides (`keys_unchanged`), the agreement on disk is the one whose digest was confirmed at phase 6 (`agreement_unchanged`), and no new package of the partner's is waiting (`theirs.incoming.json`), phase 5 ends there and says why: the partner confirms our new package on their side. With no directory step (the hand exchange) nobody has sent it, so the row says to send our new package, naming it, to them now. Phase 6 then checks the agreement digest again after compose, as above, so an unchanged agreement goes on and a changed one stops for the comparison. Phase 5 stops as before when our verifying key, our CA fingerprint, or the partner's key or CA fingerprint changed, when the agreement differs from the confirmed one, when no keys confirmation is journaled, or when a new package of the partner's is waiting (`crates/goatbuilder/tests/federate_rotate.rs`, the cases lettered a to g). The run still stops at phase 10's hand-off to plan and deploy, as every run does. A new package with another CA fingerprint, a changed key, or keys bound by hand with no keys confirmation journaled, still asks confirmation 1 in the same phase.
- **Compose checks it.** Before each phase after 5 that a run reaches, run or skipped, whatever phase it started from (`--from 6` included), so a phase in between that replaced it is caught too, the package on disk must be the last one confirmed or recorded, and, when a keys confirmation is journaled, its CA fingerprint and the keyring's key must be the ones that confirmation names; a package that cannot be read for them fails too. Either failing is GB-191, naming phase 5, and the phase it was checked before does not run: a package placed and then left for the keys (a stop, exit 0) is never composed before its keys are confirmed.
- **Measured in the federation test environment; not on standing environments.** Tested through the binary in the test world (`crates/goatbuilder/tests/federate_confirm.rs`) and the directory step against a stand-in directory (`tests/test_fed_directory.py`). **Measured** once in the federation test environment (ADR 1229's transport trial, both sides rotating in turn): after the partner's phase 11 the tunnel came back within 29 s, and strict acceptance passed on both sides. Not measured on two standing environments.

`rotate` never runs on its own initiative. Phase 8's existing rule stands: an existing leaf that fails validation is refused with "inspect it before using --rotate" (`peering_leaf_material.py:216-220`). The comment in `run.rs:25-26` said phase 8 "renews them when needed", which the helper does not do; build item 1 corrects it.

## 6. The proving scenario

The scenario proves gate row B3 in the federation test environment: each key is rotated in turn on a running peering, the command is run again on both sides, and a continuous stream of samples arrives throughout. It belongs in `ops/federation-e2e/scenarios/catalog.yaml`, beside `rerun-every-phase` (`catalog.yaml:173-196`). That scenario's check `rotation-explicit-only` (its step `rotation-only-on-request`, `catalog.yaml:195`) needs the explicit request path of §5 before it can pass.

**Unit and setup.** The `forwarder` unit (`catalog.yaml:633-635`): a pair of sovereigns (`xaa`, `xab`) peered over WireGuard through a forwarder, so that K5 is covered. Strict acceptance passes. A publisher on each side writes one numbered sample every second for the whole scenario, and a reader on the other side records each number it receives with its arrival time: `ops/federation-e2e/lib/flow.sh` (`flow_start … reader`, the receiving core's REST subscription) and `ops/federation-e2e/lib/samples.py` (`record`, and `check` for `samples-<key>`), driven by `ops/federation-e2e/units/rotation.sh` (§7 row 7).

- The ordinary command, with the new value where §5 says, runs on the other side.
- Phase 14 runs on both sides.

So a transport rotation is built that way: what is released during its gap is lost, and the check records each gap instead of failing it, when the gap fits a rotation (the `samples-<key>` row above). Two follow-ups would close the gap, neither designed: a sender-side replay of what was released while the link was down, or the two-link overlap §3 leaves out. Open: in the same run one number was lost on its own (the a2b flow's 504, released and accepted at 10:04:39Z during the acceptance run after the second rotation, outside both gaps, with its neighbours delivered); it is not the reader's stop, and its cause is not known.

**Measured** in a later run of the same scenario, with the partner's phases 11 to 13 run after its step: those phases restart the republisher on the partner's core (phase 12 changes `republisher.pem`, and the handler "Restart goat fed republisher" runs), and the republisher does not replay what was released while it restarted. The samples check puts such a number in `lost_outside`, so `samples-transport` fails on it, as it should: no rotation's gap explains it. ### 8.1 What is rotated

The IPsec transport authenticates with certificates, not with anything the package or the agreement carries. Three items belong to one peering:

| Item | Where it lives on our edge | Who makes it | Who else holds it |
|---|---|---|---|
| **Our IPsec leaf**, certificate and private key, Subject CN = `peering_edge_local_id` | `/etc/swanctl/x509/<name>-cert.pem` and `/etc/swanctl/private/<name>-key.pem` (`roles/goat-peering-edge/defaults/main.yml:165-166`), presented as `local.certs` (`templates/swanctl.conf.j2:43`) | The offline CA ceremony | Nobody: the partner checks it against our CA |
| **Our per-peering IPsec CA**, the certificate only | Not on our edge today | The offline CA ceremony | The partner, as their `<name>-partner-ca.pem` |
| **The partner's per-peering IPsec CA** | `/etc/swanctl/x509ca/<name>-partner-ca.pem` (`defaults/main.yml:167`), the only CA the connection accepts (`templates/swanctl.conf.j2:52`) | The partner | The partner |

The role treats the partner CA file as the revocation instrument: nothing on the path checks a CRL or OCSP, so a replaced leaf stays valid until its `notAfter`, and only removing the CA that issued it retires it (`defaults/main.yml:140-158`). Rotation therefore has two kinds:

- **`ipsec-leaf`**: a new leaf from the same CA. Only our side acts. The old leaf is **not** retired; it still authenticates until its `notAfter`. This is renewal before expiry, not a response to a leaked key.
- **`ipsec-ca`**: a new CA and a new leaf issued by it. Both sides act. When the partner removes our old CA, our old leaf stops authenticating at once. This is the response to a leaked key, and the only rotation that retires anything.

Receiving the partner's new CA, when the partner rotates theirs, is the same procedure with the sides swapped (§8.3, "When the partner rotates").

### 8.2 Who runs it, and where the material comes from

The role writes no secret material and refuses without it (`roles/goat-peering-edge/tasks/main.yml:304-323`), and rotation keeps that rule. The ceremony issues the new material. An operator stages it on the edge beside the live files, under the names the role reads with `.next` before the extension (`<name>-cert.next.pem`, `<name>-key.next.pem` at mode 0600, and for `ipsec-ca` the new CA certificate as `/etc/swanctl/x509ca/<name>-local-ca.next.pem`). The operator then runs:

```text
goatbuilder federate rotate <partner> ipsec-leaf
goatbuilder federate rotate <partner> ipsec-ca  --partner-holds-ipsec-ca <sha256>
```

The command never mints, copies or prints a private key. It checks the staged material on the edge, sets the live material aside, switches, re-authenticates and runs phase 14. For both kinds, a new role variable, `peering_edge_local_ca_path`, names our current IPsec CA certificate on the edge (public material) so the role can check the chain. Without it, a rotation is refused (GB-289).

Generating the new key on the edge, with only a signing request leaving it, would remove the step in which a private key travels to the edge. That changes the role's rule that it writes no secret, so it is left for a later decision and is not part of this design.

### 8.3 The order, and the overlap

**`ipsec-leaf`**, our side only:

1. **Check what is staged**, on the edge and before anything moves: the key matches the certificate; the certificate chains to `peering_edge_local_ca_path`; its Subject CN is `peering_edge_local_id`; its key is ECDSA P-384, which `peering_edge_ike_proposals` requires (`defaults/main.yml:112`); it is valid now and for at least `peering_edge_min_valid_days` more (default 30); its key is not the live leaf's (step 4 tells the leaves apart by their keys, so a leaf re-certified on the old key is refused). Any failure is refused (GB-289 for missing or unreadable files, GB-290 for the rest) and nothing is moved. Before that, also before anything moves: the running charon's strongSwan series (`swanctl --version --daemon --raw`, major.minor) must be in `peering_edge_rotation_strongswan_tested` (default 5.9 and 6.0, the measured series), or the rotation is refused (GB-341); and every other peering on the edge (each `conf.d/<name>.conf` the role wrote) must have its `certs` file in `x509/`, a readable key in `private/` that is that certificate's key, and its `cacerts` files in `x509ca/`, or the rotation is refused naming the peering (GB-343), because step 4 reloads every credential on the edge from the files alone. **Built**.
2. **Set the live pair aside** into `/etc/swanctl/.previous-<id>/` (0700), once per rotation id, as `roles/goat-peering-wg/tasks/carrier-key.yml` does for the carrier key.
3. **Switch**: move the staged pair over the live names, run `swanctl --load-creds`, then `swanctl --rekey --ike <name> --reauth`. A rekey without `--reauth` keeps the authentication of the old IKE SA, so the new certificate would not be presented until the next re-authentication.
4. **Confirm**: wait up to `peering_edge_dpd_timeout` (150 s by default, `defaults/main.yml:124`) for an established IKE SA and an installed CHILD SA (`swanctl --list-sas --ike <name>`). Once it is up and the SAs from before the re-authentication are gone, check the other peerings' files again (GB-343 if one went missing: the reload is not run, and the old pair is put back), reload the credentials from the files alone (`swanctl --load-creds --clear`), then prove the leaf from `swanctl --list-certs`. charon must list exactly one end-entity certificate of our id: the live leaf's serial, holding its private key. And the live leaf's public key must differ from the set-aside leaf's. `--list-sas` names only the identities, which an old and a new leaf share. charon signs only with a key it holds, and the partner checks the signature against the certificate we send, so an SA made under those conditions ran on the live leaf. That holds only when the key is new, because a re-certified old key would sign the same; so the key check is part of the proof, and it repeats step 1's for a resume that finds the switch already made. Anything else is a roll-back with GB-342, which says which check failed and names the serials. The record `.previous-<id>/confirmed` names the serial, the sha256 of the new and the set-aside leaf's public keys, and the strongSwan version. This is an inference from what charon holds, not an observation of the certificate sent. **Built**, and **measured** on a real charon (strongSwan 5.9.8 on Debian 12 and 6.0.4 on Ubuntu 26.04, lab hosts, test certificates):
   - After the switch's `--load-creds`, charon no longer holds the old key but still lists the old certificate. `--flush-certs` does not drop it (it empties only the cache of certificates received); `--load-creds --clear` does, and the IKE SA stays up through it, with the same SA id.
   - With two peerings on one charon, one `--load-creds --clear` for the rotated peering leaves the other peering's IKE SA up with the same id. Forty clears back to back, while the other peering re-authenticated from either side and rekeyed, left it up. On 6.0.4 one re-authentication attempt that started during a clear failed with "no private key found"; make-before-break kept the existing SA, and a following re-authentication succeeded. On 5.9.8 none failed in that run.
   - **Not built**: a check on the partner's side of the serial they received. It is stronger, and possible where both sides run goatbuilder, because only the partner sees the certificate that was sent.

   If the SA does not come up, **roll back**: move the set-aside pair back, load it, re-authenticate, write `.previous-<id>/rolled-back`, and stop with GB-302. During `ipsec-leaf` the old leaf is still valid under an unchanged CA, so the roll-back restores the link. The marker is written before the old pair is restored, so a run killed during the roll-back resumes by finishing it. A rolled-back rotation stays rolled back: every later run of its id, a resume or a retire, reports GB-302 with the old leaf live, moves nothing and never replaces our CA; a new attempt takes a new id. **Built** (`tasks/rotate-switch.yml`).
5. Phase 14.

**`ipsec-ca`**, three steps, both sides. The overlap runs from step 1 to step 3: during it, the partner accepts leaves under our old and our new CA.

1. **Announce.** We deliver our new CA certificate to the partner, as the old one was delivered, and both sides read its sha256 fingerprint aloud on the call, as confirmation 1 does for keys. The partner places it with a new role variable, `peering_edge_remote_ca_next_path`. When that variable is set, the role renders `remote.cacerts` as the current file and the next one, comma-separated, which strongSwan accepts as a list. The partner runs `goatbuilder federate <us> --from 11` and reads back the fingerprint of the file they placed.
2. **Switch.** We run `rotate <partner> ipsec-ca --partner-holds-ipsec-ca <sha256>`. Without the flag, or with a fingerprint other than our staged CA's, the switch is refused (GB-303) before anything moves: we have no way to read the partner's trust store, so the read-back is the only evidence that they will accept the new leaf. The staged checks are those of `ipsec-leaf`, except that the leaf must chain to the staged new CA. Then steps 2 to 5 of `ipsec-leaf` run. The roll-back works here too, because the partner still trusts the old CA. The new CA then becomes our `peering_edge_local_ca_path`.
3. **Retire.** After phase 14 passes on both sides on the new leaf, the partner moves our new CA over their current file, unsets `peering_edge_remote_ca_next_path` and runs `--from 11` again. Our old leaf now fails at their edge: that is the revocation. Our next run of the command removes the set-aside private key and keeps the set-aside certificate, so a retired key does not stay on the edge. **Built** as `tasks/rotate-retire.yml`, which never runs the switch: it never moves the live pair, the staged pair or our CA, and removes the set-aside key only once the new leaf is live (the confirm wrote `.previous-<id>/confirmed`, with the unique id of the IKE SA the re-authentication made and the time, before the rotation reported success, and only once every SA from before the re-authentication was gone, since an old-leaf SA left up could later rekey into one established after the record; an SA from before still up when the window closes is a GB-302 roll-back, and a roll-back removes the record. A record without its `id=` or `at=` line is refused as unreadable; the live pair is not the set-aside one; the live key is the live certificate's; and that SA, or one established after the confirm's time, has an installed CHILD SA). Without the record it refuses (GB-309, "not confirmed"), and a re-run with the same id re-authenticates and confirms, never "done": the rekey before the re-authentication makes an SA established after the set-aside that still runs on the old leaf, so the set-aside's time proves nothing. An id with no `.previous-<id>/` on the edge, or a rotation not confirmed live, is refused (GB-309); a rolled-back one, GB-302. Our new CA replaces the current one only on the switch, with the partner's read-back (GB-303). `swanctl --list-sas` does not name the certificate an SA authenticated with, so "live" is the SA the re-authentication made (recorded by the confirm), or one established since, with the switched pair in place. The confirm proved, at its time, that the live leaf was the only one of our id charon could sign with (step 4); the retire step does not repeat that check.

**Compromise.** When our old leaf's key is believed leaked, the overlap is itself the exposure. `--no-overlap` skips step 1: the partner replaces our CA directly, the link is down from their phase 11 until our switch, and the switch checks the read-back as before. The roll-back is then impossible, because the partner no longer trusts the old CA, and the command says so before it switches.

**When the partner rotates.** We are the partner side. Their new CA goes into `peering_edge_remote_ca_next_path` and we run the ordinary command from 11, then read the fingerprint back to them. At their retire, we move it over `peering_edge_remote_ca_path`, unset the variable and run from 11 again. No new verb is needed.

### 8.4 How a killed run finishes

**Built:** `<work>/.rotation-ipsec` on the controller holds the rotation's kind, id and, for `ipsec-ca`, the partner's read-back. It is written before phase 11, only by a run that includes phase 11, and removed once phase 11 passed. A run that finds it resumes that rotation with the same id, and a run of another kind or read-back is refused (GB-298), naming the id; read-backs are compared as fingerprints (`sha256:` and lowercase), and an empty or corrupt record is refused with its own message. `<work>/ipsec-rotations.json` keeps every rotation with its read-back and when it started, switched (phase 11 passed), was accepted (phase 14 passed here after the switch: this side's phase 14 only; the partner's is confirmed on the call) and was retired: it is what allows a retire, and what makes a new rotation wait for the last one's retire. A ledger update that fails after its phase passed is shown as a warning row, naming the file. A phase 11 with no play to pass the rotation to is refused rather than run plain (GB-328). The edge's `.previous-<id>/` carries the steps, as below. **Designed, not built:** the fuller journal of this paragraph and `--abandon`. Each rotation writes `<work>/ipsec-rotation.json` on the controller before anything moves on the edge: the kind, the rotation id, the sha256 of the staged certificate (and of the staged CA for `ipsec-ca`), the partner's read-back fingerprint, and the last step that completed (`checked`, `set-aside`, `switched`, `confirmed`, `retired`). The set-aside directory `.previous-<id>/` on the edge is the second marker. A resumed run takes the peering's lock, reads the journal, and redoes each step only when its effect is missing:

- **Set aside**: only when `.previous-<id>/` does not exist, so a second run never sets aside the new pair as if it were the old one. **Built** so that it exists only complete: built in `.previous-<id>.tmp`, synced to disk (`sync -f`) and renamed into place; a leftover `.tmp` (a run killed during the set-aside, when the live pair is still the old one) is discarded and the set-aside redone, so a later roll-back restores both files.
- **Switch**: only when the live certificate's sha256 is not the journal's. **Built** for a run killed between the switch's two moves: when one staged file is moved in and the other is still staged, the next run finishes the remaining move if the file left is the moved one's match (the moved file is not the set-aside one, and the two halves are one key pair, each parsed: a file openssl cannot parse gives no digest and so matches nothing), and otherwise refuses with GB-311 and moves nothing, so the live pair is never left mixed. A run killed after the move but before `--load-creds` finds the files switched, and charon still holding the old credentials in memory. It loads and re-authenticates without moving anything.
- **Re-authenticate and confirm**: always repeated, which is harmless.
- **Roll back**: a run killed during the roll-back finishes it. The set-aside pair is the target, and a live file whose sha256 matches the set-aside one is already done.

A journal whose staged sha256 differs from the `.next` files now on the edge (someone staged other material during a stopped rotation) is refused (GB-298). The operator either restores the files the journal names, or finishes the rotation with `--abandon <id>`, which moves the set-aside pair back if it is not live and removes the journal. No path deletes the set-aside pair before the retire step.

### 8.5 Refusal codes

Ten codes, GB-289, GB-290, GB-298, GB-302, GB-303, GB-309, GB-311, GB-341, GB-342 and GB-343, reserved for this design. Each prints the host, the file and the fix:

| Code | Refused when |
|---|---|
| GB-289 | A staged file, or `peering_edge_local_ca_path`, is missing or unreadable, or the staged key is not mode 0600 |
| GB-290 | The staged certificate does not match its key, does not chain to the CA it must chain to, names another CN, uses another key type than the proposals require, is not valid now and for the minimum days, or is on the live leaf's key |
| GB-298 | A resumed rotation whose journal names material other than what is staged, or another rotation of this peering is unfinished |
| GB-302 | The IKE SA did not come up on the new leaf within `peering_edge_dpd_timeout`; the old pair was restored (or, with `--no-overlap`, could not be). Also every later run of a rotation id that was rolled back |
| GB-311 | A switch stopped half way, and the staged file left is not the moved one's match; nothing is moved |
| GB-309 | The retire step finds no `.previous-<id>/` for the id, or the rotation is not confirmed live; nothing is removed |
| GB-341 | The running charon reports a strongSwan series (major.minor) outside `peering_edge_rotation_strongswan_tested` (5.9 and 6.0, the measured ones), or `swanctl --version --daemon --raw` does not report one; nothing is moved |
| GB-342 | The new SA came up, but after `--load-creds --clear` charon does not list exactly one end-entity certificate of our id, the live leaf's serial with its key, on a key other than the set-aside leaf's; the old pair was restored |
| GB-343 | Another peering on the edge lacks its certificate, its key or its CA files, which `--load-creds --clear` would unload: refused before anything moves, or, just before the reload, the old pair restored |
| GB-303 | `ipsec-ca` without `--partner-holds-ipsec-ca`, or with a fingerprint other than the staged CA's. The role checks it too, from `peering_edge_rotation_ca_readback` |

A `rotate … ipsec-*` on a peering whose agreement is not `ipsec-fips` is refused with the stage's existing usage code, GB-189.

### 8.6 Tests

Written before the code, as for the other keys:

- **Role, with a stand-in `swanctl` and test certificates made at test time** (as `roles/goat-peering-wg/tests/test-rotation.sh` makes its keys): a key that does not match its certificate, a wrong CN, a certificate from another CA, an RSA key, and one expiring within the minimum days are each refused, and nothing on disk changes. A good pair is set aside once per id, and a second run with the same id moves nothing. A run stopped after the set-aside, and one stopped after the move, each finish without a second move and with exactly one `--load-creds` and one `--reauth` after the resume. A stand-in that never reports an established SA makes the run restore the old pair and exit with GB-302, and a resume or retire of that id reports GB-302 again with the old leaf live. The stand-in keeps the credentials charon holds as measured: a `--load-creds` keeps a certificate whose file is gone and only the keys on disk, `--clear` holds only what is on disk. After a good switch the old leaf is no longer listed, and the record names the serial, both keys and the version. A charon that never loaded the new pair, one that also holds the old pair under other file names, and a resume that finds a leaf on the set-aside key switched in are each a GB-342 roll-back that names the serial; a staged leaf on the live key is GB-290. Another peering whose certificate, key (missing or unreadable) or CA file is gone is GB-343 before anything moves; one whose key goes during the rotation is GB-343 with no reload and the old pair back; one with its files in place keeps its leaf and key loaded; strongSwan 5.8.4, 6.1.0, or a version that cannot be read is refused with GB-341 before anything moves, and 6.0.4, or 5.8.4 with the list widened, rotates. The retire step removes the set-aside key and keeps the certificate; with the next leaf staged it moves neither pair; an unknown id, a retire before the switch, or one with the SA down is refused with GB-309; it never replaces our CA.
- **Template**: without `peering_edge_remote_ca_next_path`, `swanctl.conf` renders byte for byte as today; with it, `remote.cacerts` lists the current file and then the next.
- **goatbuilder unit and binary tests**: the stage keys parse, and are refused for a WireGuard agreement with GB-189. `ipsec-ca` is refused without the read-back and with a wrong one (GB-303). The journal resumes at the right step, and a mismatched journal is GB-298. A peering with no rotation renders phase 11 exactly as before.
- **Not covered by this design's tests**: the federation test environment has no `ipsec-fips` unit (§6 uses the `forwarder` unit), and strongSwan in a container needs the `xfrm` interface and privileges the environment does not grant. So the samples-throughout check for K6 needs a new unit, which is not designed here. The role sets `make_before_break = yes` in its charon drop-in (`peering_edge_make_before_break`), rather than leaving it to the packaged strongSwan, whose default has changed between releases and whose version the role does not pin (a rotation checks the running series, GB-341); not measured on a running link whether the switch then has any gap. The first apply after that drop-in change restarts strongSwan once on each ipsec-fips edge (the drop-in notifies the restart), a brief drop of that peering's link, so both sides of a peering are applied in one window; whether `--reload-settings` would make charon take `make_before_break` without a restart is not shown, so the restart stays. Because the old IKE SA stays ESTABLISHED while the new one negotiates, the confirm counts only an SA whose unique id was not up before `--reauth`. An IKE rekey also makes a new SA id with a fresh established time but keeps the old authentication, and each side schedules its own (rekey_time minus a random part up to rand_time), so a rekey the partner starts can land in the confirm window while ours is hours away. The rotation therefore always rekeys first when an IKE SA is up (`swanctl --rekey`, no `--reauth`) and waits for it, which restarts both sides' timers, and notes the ids after it; a rekey that does not complete is a GB-302 roll-back before any re-authentication. A rotation refuses before anything moves unless `peering_edge_ike_rekey_time` minus `peering_edge_ike_rand_time` exceeds the confirm window plus `peering_edge_rotation_rekey_margin_seconds`. The rekey and unique-id behaviour is strongSwan's as documented, not measured here. The confirm counts only the id the re-authentication made, and the retire step only the SA the confirm recorded in `.previous-<id>/confirmed`, or one established after the confirm's time (strictly, to the second, as `swanctl --list-sas` prints ages).
