# GB-343: another peering's credentials on the edge are missing, so the IPsec rotation does not reload them

Generated from `ops/errors/catalog.yaml` by `ops/ci/check-error-catalog.py --write`; do not edit here. `GB-343` is printed by `goatbuilder`. The same text offline: `goat explain GB-343` or `goatbuilder explain GB-343`.

## What it means

Once the new IKE SA is up, an IPsec credential rotation (goat-peering-edge) reloads every credential in the edge's swanctl directory from the files alone (swanctl --load-creds --clear), which unloads any key whose file is gone. So before anything moves, and again just before that reload, it checks every other peering on the edge (each conf.d/&lt;name>.conf the role wrote): its certs file in x509/ is present and readable, a readable key in private/ is that certificate's key, and its cacerts files in x509ca/ are present and readable. One was not; the message names the peering and the file. Before anything moves, nothing was moved. Just before the reload, the reload was not run, the old pair was put back and the rotation is marked rolled back.

## Why it happens

- another peering's certificate, key or CA file was removed or made unreadable
- a peering was removed by hand, leaving its conf.d file behind

## What to do

One line per step or alternative:

```text
run that peering's role again so its files are written, or remove the peering, then run the rotation (a new id after a roll-back)
```
