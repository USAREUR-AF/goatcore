# GB-388: rows only the node holds have not been accepted

Generated from `ops/errors/catalog.yaml` by `ops/ci/check-error-catalog.py --write`; do not edit here. `GB-388` is printed by `goatbuilder`. The same text offline: `goat explain GB-388` or `goatbuilder explain GB-388`.

## What it means

Every site writes (ADR 1165), so a node being rebuilt may hold rows its founder lacks. The rebuild's export step compared each table of the founder's replication sets with the founder, by primary key and row digest, and wrote the rows only the node holds, or holds changed, to the export file beside the journal (mode 0600). Rows written here after the founder's last applied commit from the node are replayed after the copy. The others are for review: they came from another site, or the founder removed them since. The file also names each table that is not replicated, holds rows and references a table the copy truncates (on an identity database, the site's sessions), which the truncate empties. The step refuses until it is run with `--accept` and the digest it printed, so nothing is truncated before an operator has read them. The reseed step refuses with this code too when the rows only the node holds changed after the export: the export step then runs again. Nothing was changed.

## Why it happens

- the node took writes while it was cut off, and the founder never received them
- the founder removed rows while the node was cut off, and the node still holds them
- a write reached the node after the export step (the reseed step's case)

## What to do

One line per step or alternative:

```text
read the export file the line names; then run the rebuild again with --accept <digest>
goatbuilder join-node <env> --site <site> --node <node> --class <class> --reseed --accept <digest>
```
