# GB-313: phase 8 refused the edge's certificate request for an edge leaf

Generated from `ops/errors/catalog.yaml` by `ops/ci/check-error-catalog.py --write`; do not edit here. `GB-313` is printed by `goatbuilder`. The same text offline: `goat explain GB-313` or `goatbuilder explain GB-313`.

## What it means

On a two-driver peering the edge makes its two leaf keys and sends only their certificate requests, which phase 8 signs with our CA (mint-peering-leaves.sh --request, peering_leaf_material.py). A request is signed only when its subject is exactly one attribute, CN = the name phase 8 derives for that leaf, it carries no extension or attribute, its key is EC P-256, it is signed with ECDSA and SHA-256 or stronger and its self-signature verifies, and its key is new: not the other request's, not our CA's, not another leaf's in the output folder or a previous set there, and not one the key record lists as signed before. The certificate's names come from the agreement, never from the request. One request failed, so neither edge leaf was signed and nothing was written.

## Why it happens

- the request was made with another name, or with extra subject attributes, extensions or attributes
- the edge's key is not P-256, or the request is signed with SHA-1 or another weak algorithm
- the edge reused a key: the same key for both leaves, our CA's key, a controller leaf's key, or a key signed for this peering before (the key record outlives the output folder)
- the request file was changed on the way, or holds anything besides one request

## What to do

One line per step or alternative:

```text
run phase 2's edge half again on the edge driver, so the edge makes new keys and requests, import its result, then run phase 8 again
read the refusal: it names the leaf and the rule the request broke
```
