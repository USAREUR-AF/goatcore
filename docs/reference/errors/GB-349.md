# GB-349: a table differs after the copy

Generated from `ops/errors/catalog.yaml` by `ops/ci/check-error-catalog.py --write`; do not edit here. `GB-349` is printed by `goatbuilder`. The same text offline: `goat explain GB-349` or `goatbuilder explain GB-349`.

## What it means

The re-seed's last step compares each copied table on the node and the founder by row count and digest, and one still differs after the wait. The node and the founder do not hold the same rows.

## Why it happens

- writes still arriving on one side: a busy table converges a little later
- a write the copy did not carry, or a conflict resolved differently on each side

## What to do

One line per step or alternative:

```text
run the re-seed again; it starts at this step and compares again
compare the table with drift-watch, as the post-partition convergence runbook's step 4 does
```
