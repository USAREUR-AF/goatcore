# GB-298: an IPsec rotation under way is not the one asked for

Generated from `ops/errors/catalog.yaml` by `ops/ci/check-error-catalog.py --write`; do not edit here. `GB-298` is printed by `goatbuilder`. The same text offline: `goat explain GB-298` or `goatbuilder explain GB-298`.

## What it means

goatbuilder federate rotate &lt;partner> ipsec-leaf|ipsec-ca records the rotation it starts in &lt;work>/.rotation-ipsec (its id, its kind and, for ipsec-ca, the partner's read-back of our new CA) before phase 11 runs, and removes the record once phase 11 passed. A run that finds a record resumes that rotation with the same id, so goat-peering-edge sets nothing aside twice. This run asked for another kind, or another read-back, than the record names, so it was refused before anything ran.

## Why it happens

- an earlier rotation stopped before phase 11 passed, and a rotation of the other kind was asked for
- the partner's read-back changed between the run that started the rotation and this one

## What to do

One line per step or alternative:

```text
finish the rotation the record names with the command that started it (the message names its id and kind)
or remove <work>/.rotation-ipsec to start again; the edge keeps the set-aside pair in /etc/swanctl/.previous-<id>/
```
