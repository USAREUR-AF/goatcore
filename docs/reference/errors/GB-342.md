# GB-342: the IPsec rotation's new SA could not be shown to run on the new leaf; the old pair was put back

Generated from `ops/errors/catalog.yaml` by `ops/ci/check-error-catalog.py --write`; do not edit here. `GB-342` is printed by `goatbuilder`. The same text offline: `goat explain GB-342` or `goatbuilder explain GB-342`.

## What it means

swanctl --list-sas names only the identities, which an old and a new leaf share, so goat-peering-edge proves the leaf another way. Once the new IKE SA is up and the SAs from before the re-authentication are gone, it reloads the credentials from the files alone (swanctl --load-creds --clear) and reads swanctl --list-certs. charon signs only with a private key it holds, and the partner checks the signature against the certificate we send, so the new SA ran on the live leaf when charon lists exactly one end-entity certificate of our id (peering_edge_local_id): the live leaf's serial, holding its private key, on a key other than the set-aside leaf's. Here it did not: charon lists another certificate of our id, does not hold the live leaf with its key, or the live leaf has the set-aside leaf's key. The message says which and names the serials. The old pair was put back and loaded, the old leaf is live, nothing was recorded, and the rotation is marked rolled back, so every later run of its id reports GB-302.

## Why it happens

- another certificate and key of our id are still in the swanctl directory under other file names
- charon did not load the new pair
- the live leaf was re-certified on the old key, and a resume found it switched in

## What to do

One line per step or alternative:

```text
read swanctl --list-certs on the edge; remove every certificate and key of our id but the ones the rotation stages, then stage the new pair again and start a rotation with a new id
have the ceremony issue the leaf on a new key
```
