# GB-391: rows only the node held were not written back

Generated from `ops/errors/catalog.yaml` by `ops/ci/check-error-catalog.py --write`; do not edit here. `GB-391` is printed by `goatbuilder`. The same text offline: `goat explain GB-391` or `goatbuilder explain GB-391`.

## What it means

After the copy, the rebuild's replay step wrote each exported row to replay back on the node, one statement per row, parents before children, so it replicates to the founder. At least one row was not written (a key or a check refused it, or the row is now present with other contents). Each such row, with the reason, and the rows for review are in the hand-back file beside the journal (mode 0600). The step refuses until it is run with `--accept` and the hand-back's digest. The rows that were written stay written.

## Why it happens

- another site wrote a row with the same unique value (an email, a name) while the node was cut off
- a row's parent was for review, not replayed, so its foreign key refuses it
- a trigger on the node refuses the write (a hub-only change made at a joiner)

## What to do

One line per step or alternative:

```text
read the hand-back file the line names; apply or discard each row by hand, then run the rebuild again with --accept <digest>
```
