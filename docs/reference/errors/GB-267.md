# GB-267: this part of a two-driver peering is not built yet

Generated from `ops/errors/catalog.yaml` by `ops/ci/check-error-catalog.py --write`; do not edit here. `GB-267` is printed by `goatbuilder`. The same text offline: `goat explain GB-267` or `goatbuilder explain GB-267`.

## What it means

A peering declared with two drivers (`drivers: two`) is handed off between the edge driver and the controller only at phases 1 and 2, where the hand-off is built. Three cases are refused before anything runs: the edge driver's own run (`goatbuilder federate <partner> --side edge`, with or without the `--expect-commit` a hand-off object names), the controller's `goatbuilder federate import`, which is not built either, and a two-driver run that would reach a phase after 2 that needs the edge (3, 11, 12, 13 or 14), whose hand-off is designed and not built. That includes every `goatbuilder federate deploy`, which runs phase 10 then 11: it is refused before its plan is approved or rechecked, so phase 10 never admits the edge on our core.

## Why it happens

- goatbuilder federate &lt;partner> --side edge was run on the edge driver, as a hand-off object's command names it
- goatbuilder federate import &lt;partner> &lt;phase> &lt;result> --sha256 &lt;code> was run, as a hand-off object's import names it
- a two-driver run that would reach phase 3, 11, 12, 13 or 14, such as --from 3, --from 4 with no --to, or goatbuilder federate deploy (a run from 4 to 10 is not refused)

## What to do

One line per step or alternative:

```text
run the peering with one driver for now: remove drivers: two from its peerings: entry, from a machine that reaches both the edge host and the core host
```
