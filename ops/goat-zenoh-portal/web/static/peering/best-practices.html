Pub/Sub Best Practices

The single most common mistake new __LEX_ORGS__ hit on the fabric is treating pub/sub like an S3 bucket. It isn't. This page tells you the mental model that actually applies, gives you the topic-design patterns that cover ~95% of real use cases, and shows the three footguns that produce the symptom "I published but my subscriber didn't receive anything."

The fabric is Zenoh under the hood, but these principles apply to any pub/sub system (MQTT, NATS, Kafka, Solace, …). If you've worked with those, jump to the footguns.

1. The mental model: a topic is a channel, not a bucket

If you come from object-storage backgrounds (S3, GCS, Azure Blob), it's natural to reach for the model "every object gets a unique key; you PUT the bytes; you GET the bytes back by key." That model is wrong for pub/sub. Here's what's actually happening:

You expect (S3 model) What actually happens (pub/sub model)
Each PUT creates a uniquely-keyed object that lives until I delete it Each put is a message broadcast onto a channel named by the key. Live subscribers on that channel receive it; if no one's listening, the message is gone.
GET retrieves the object stored at that key Two different operations: subscribe watches a channel for future messages, get queries a storage that may or may not be configured for that channel.
The bucket is the namespace; individual object keys hold the data The topic path is the channel name. Subscribers can pick one channel, or pattern-match many channels at once. Choosing what to put in the path is a design decision with real consequences.
Object names are arbitrary identifiers Topic paths are patterns subscribers will match against. If your path embeds random UUIDs that subscribers can't predict, only wildcard subscribers will work.

The corollary that matters: the topic path is your contract with subscribers, not just a unique label for your data.

2. Four topic-design patterns (pick one consciously)

The decision you have to make for each piece of data you publish: what shape does your topic path take, and what does that imply for subscribers and for storage?

Pattern A — Single channel, all events: __LEX_ORG__/system/v1

One topic; every message goes to the same key.
# Publisher:
session.put("acme/router/cot/v2", cot_xml_bytes)

# Subscriber:
session.declare_subscriber("acme/router/cot/v2", handler)
  • Best for: continuous event streams where consumers want "everything that happened on this channel."
  • Storage behavior: rocksdb-style storages keep only the latest value per key — this pattern preserves only the most recent event in history. If you need replay of every event, use Pattern C.
  • Subscriber gotcha: literal key, no wildcard needed. Simple.

Pattern B — Per-entity state: __LEX_ORG__/system/v1/<entity-id>

One topic per logical entity, stable key per entity.
# Publisher (entity X's latest state):
session.put(f"acme/router/cot/v2/{entity_uid}", cot_xml_bytes)

# Subscriber (all entities, live):
session.declare_subscriber("acme/router/cot/v2/*", handler)

# OR get latest known state for a specific entity (queryable history):
session.get(f"acme/router/cot/v2/{specific_entity_uid}", queue)
  • Best for: "latest known state per object" semantics — vehicle tracks, sensor positions, anything where consumers want "what's entity X doing right now?"
  • Storage behavior: rocksdb keeps the latest message per entity. Storage size scales with number of entities, not number of events.
  • Subscriber gotcha: wildcard required if you want all entities. Use /* to match exactly one segment (the entity UID); use /** to match any depth.

Pattern C — Per-event archive: __LEX_ORG__/system/v1/<entity-id>/<event-id> or __LEX_ORG__/system/v1/<uuid>

Every message gets its own unique key.
# Publisher (fresh UUID per message):
session.put(f"acme/router/cot/v2/{uuid.uuid4()}", cot_xml_bytes)

# Subscriber (live tap):
session.declare_subscriber("acme/router/cot/v2/**", handler)

# OR query history (returns every event ever stored):
session.get("acme/router/cot/v2/**", queue)
  • Best for: archival / audit / replay workloads where every individual event must be queryable in retrospect.
  • Storage behavior: every message is a new key; rocksdb stores all of them up to the configured time-to-live (7 days on the trial fabric). Storage size scales with event volume, which can be large.
  • Subscriber gotcha: wildcard is mandatory. Subscribers using a literal key never match. This is the most common failure mode on the trial fabric.

Pattern D — Request/reply via queryables

Not a pure pub/sub pattern — Zenoh queryables.

Out of scope for this page; covered in the Peering Guide walkthrough.

Picking between B and C

If a downstream consumer asks "what's the current state of entity X?", use Pattern B. If they ask "give me every event entity X has ever emitted," use Pattern C. If both, use Pattern C and have consumers do the latest-state dedup in their client, OR run two publishers (one B, one C) on different topic prefixes.

CoT specifically: the Cursor on Target XML format already carries uid="..." as an attribute inside the payload — that's the canonical entity identity. If you're publishing CoT and your consumer wants "latest known position per track," Pattern B with the CoT uid in the topic path is correct: acme/router/cot/v2/<cot-uid>. Don't mint a fresh UUID per message for the topic path — that's Pattern C, which has different consumer ergonomics and accumulates entries proportional to message rate, not entity count.

Registering the format: register these topics with format: xml so the payload is declared as application/xml rather than opaque raw bytes. If you want the portal to hold a schema for the CoT event structure, register format: xml:event and upload your CoT .xsd via the per-row schema button (the .xsd must declare a top-level <xs:element name="event">). The bytes on the wire are identical either way — the format string is registry metadata, not a wire transform. With the .xsd uploaded, the schema viewer renders the CoT data dictionary, per-language code tabs (Rust/Go/Python/TypeScript), and inspector sample-decode — the same surfaces protobuf topics get.

3. The three footguns

If you're seeing "my subscriber didn't receive anything," it's almost always one of these:

Footgun 1: Literal subscriber against a wildcarded publish

# Publisher puts to a unique-per-event key:
session.put(f"acme/router/cot/v2/{uuid.uuid4()}", payload)

# Subscriber waits on the literal parent:
session.declare_subscriber("acme/router/cot/v2", handler)   # WRONG — never matches

The publisher's key is acme/router/cot/v2/<some-uuid>. The subscriber's literal key is acme/router/cot/v2. In Zenoh's key-expression matching, those are different keys. The subscriber sees nothing.

Fix: add /** (any depth) or /* (exactly one more segment):

session.declare_subscriber("acme/router/cot/v2/**", handler)   # RIGHT

Footgun 2: Subscriber not alive at publish time

Live pub/sub has no backlog. If your publisher fires before any subscriber declares interest, the message is forwarded to whatever subscribers exist (could be zero) and then it's gone. Storage helps late joiners query history, but it doesn't replay live samples retroactively.

# This shape works only if you keep the subscriber process alive:
sub = session.declare_subscriber("acme/**", handler)
# ... your publisher in another window puts messages now ...
# sub is alive — receives them.

# This shape fails:
session.put("acme/router/cot/v2/abc", payload)   # router has no subscribers, drops
sub = session.declare_subscriber("acme/**", h)   # too late

If pub + sub are in the same script, declare the subscriber before any put, and give the declaration time to round-trip to the router. If pub + sub are in separate processes, start the subscriber first and verify it's actually connected before you fire the publisher.

Footgun 3: Subscriber session silently failed to connect

zenoh.open() doesn't always raise when the underlying TLS link fails to establish — depending on config, it can return a "session" that's not actually peered with any router. declare_subscriber on that session succeeds locally but never registers with the router, and no samples arrive.

Verify the session is actually peered before relying on it:

session = zenoh.open(config)
# Do a session.get against a known-good admin key and confirm at least one reply.
# If zero replies, your TLS handshake probably failed silently:
replies = session.get("@/*/router", zenoh.Queue())
got_any = False
for r in replies:
    got_any = True
    break
if not got_any:
    print("ERROR: session not actually peered with the router")
    sys.exit(1)

The router endpoint, cert paths, and mTLS posture are all in your onboarding bundle's first-publisher.py. If you copy that scaffolding and your subscriber matches its session-config shape, the silent-fail mode goes away.

4. Storage isn't a message bus

The fabric has rocksdb storages configured per __LEX_ORG__. They're a queryable cache of latest known values per key, not a backlog of live messages. Two implications:

session.get(key) returns the LATEST value at that key, not the history of puts to it.

If you publish 1,000 messages to the same key (Pattern A), get returns one message — the most recent one. To preserve event history, you need unique keys per event (Pattern C).

session.get is a query, not a subscription.

It returns once with the current state. To receive future updates, use declare_subscriber. A common shape combines both: query for current state at startup, then subscribe for live updates.

# At startup: get current state of every track:
replies = session.get("acme/router/cot/v2/*", zenoh.Queue())
for r in replies:
    handle_track(r.ok.key_expr, r.ok.payload)

# Then subscribe for live updates going forward:
session.declare_subscriber("acme/router/cot/v2/*", handle_track_update)

5. Payloads larger than ~2 MB

Pub/sub fabrics are tuned for many small messages, not for a few large ones. The default behaviors below kick in around 2 MB; expect silent failure modes above that size unless you actively design around them.

What Zenoh does by default

The transport layer fragments large samples across the underlying TCP/TLS link and the subscriber side reassembles. So a multi-megabyte put doesn't fail at the wire — your publisher returns "clean" and the bytes reach the router. The failure modes are downstream of that.

What we've seen on the trial fabric

A 12.5 MB put from a properly-configured __LEX_ORG__ under their prefix's storage stanza returned cleanly from the publisher but the bytes never persisted to the per-__LEX_ORG__ rocksdb dir on the router. The storage backend silently dropped the reassembled sample — no error to the publisher, no entry in the audit log indicating a storage commit failure. Live subscribers (if any had been online) might have received the sample over the wire, but session.get afterward returned nothing.

That's the behavior to expect from any pub/sub system under default configuration: the wire path is more permissive than the storage path, so an artifact too big for storage just evaporates after delivery to live subscribers (and even those have receive-side buffer caps).

Sizing thresholds (rules of thumb on the trial fabric)

Payload sizeExpected behavior
< 64 KBComfortable across the wire, storage, and audit log. Audit captures the full payload bytes (base64 in NDJSON).
64 KB – 1 MiBLive subscribers fine; storage persists; audit captures metadata + payload. Schema-body uploads via the portal use this range (1 MiB hard cap).
1 MiB – 2 MiBLive subscribers fine; storage persists; audit captures metadata but drops the payload bytes (payload_bytes_b64 absent above ~1 MiB).
2 MiB – 16 MiBTreat as not-persisted. Live subscribers MAY receive (depends on their reassembly buffer); storage drops silently. session.get will not return your bytes.
> 16 MiBDon't. Even live delivery becomes unreliable.

Pattern E — Chunk it

Split the artifact into N keys under a sub-prefix and publish each chunk under the 2 MB threshold. Subscribers reassemble in order.

# Publisher:
chunk_size = 1_500_000   # 1.5 MB — comfortably under storage cap
for i in range(0, len(payload), chunk_size):
    chunk = payload[i:i+chunk_size]
    session.put(f"__LEX_ORG__/artifact/openapi/v1/chunk/{i:08d}", chunk)
session.put("__LEX_ORG__/artifact/openapi/v1/manifest",
            json.dumps({"chunks": ceil(len(payload)/chunk_size),
                        "size": len(payload),
                        "sha256": sha256(payload).hexdigest()}).encode())

# Consumer:
manifest = json.loads(session.get("__LEX_ORG__/artifact/openapi/v1/manifest").payload)
chunks = []
for i in range(manifest["chunks"]):
    chunks.append(session.get(f"__LEX_ORG__/artifact/openapi/v1/chunk/{i*1_500_000:08d}").payload)
payload = b"".join(chunks)

Each chunk persists in storage independently; consumers get the manifest first, then walk the chunks. Treat the manifest as the canonical "is the artifact ready" signal.

Pattern F — Treat the artifact as schema material

If the artifact IS a schema (a .proto, a .fds, or — yes — an OpenAPI spec interpreted as schema-of-API), upload it to the portal's schema endpoint with format=json (or format=protobuf-source for protos). The portal's schema body cap is 1 MiB per upload, so still needs chunking for >1 MiB artifacts. Schemas are queryable from the portal UI at /schema.html?key=<topic> without going through Zenoh storage at all.

Pattern G — External storage pointer

Publish a small "blob handle" message (URL + content-hash + size + content-type) under a normal topic. Store the artifact in one __LEX_ORG__-owned object store (MinIO, S3, etc). Consumers fetch the handle via Zenoh, then GET the artifact from the object store.

session.put("__LEX_ORG__/artifact/openapi/v1/handle",
            json.dumps({"url": "https://__LEX_ORG__-bucket.example/openapi/v1.json",
                        "sha256": "...", "size": 12_500_000,
                        "content_type": "application/json"}).encode())

This is the right shape for artifacts that are large AND infrequently updated AND have existing object-store delivery infrastructure.

Pattern H — Queryable

__LEX_ORG_TITLE__ stands up a queryable that responds to session.get requests with the artifact materialized from their own process. No fabric storage involved; the artifact lives in __LEX_ORG__ memory or local disk. Good when the artifact is computed or project-specific.

What NOT to do

  • Don't treat __LEX_ORG__/path/big-artifact as your single retrieval URL with a multi-MB body in the put. That's the S3 model from §1 again; it doesn't work here for payloads above the storage cap.
  • Don't rely on the publisher's "clean return" as confirmation that the artifact persisted. The wire and the storage paths have different size budgets; the publisher only sees the wire success.
  • Don't assume the audit log will tell you a large put dropped. The audit subscriber records that the publish happened (with metadata) but may not flag a storage-side drop.

Confirming persistence

For any single put you want to know whether storage actually captured, the canonical end-to-end test is:

  1. put your bytes
  2. Wait ~1 second
  3. get the same key from a fresh session
  4. Compare the SHA256 of returned payload to what you put

For chunked artifacts (Pattern E), additionally verify the manifest chunks-count matches the count you wrote, and each chunk's hash matches before assembly.

If get returns nothing or returns a truncated payload, the artifact exceeded a downstream cap. Drop to a smaller chunk size or move to Pattern G.

6. The audit log isn't your retrieval surface

The fabric's audit subscriber captures every put on ** into object storage. That's for compliance and forensics, not for normal consumer retrieval. Don't build your consumer to scrape audit objects — use session.get or declare_subscriber against the router instead.

7. Worked example: CoT publisher + subscriber done right

This is the shape we'd ship in each __LEX_ORG__'s first-subscriber.py in the onboarding bundle. Pattern B (per-entity state) matches CoT's typical use case.

# publisher.py — publishes one CoT event per track per tick
import zenoh, uuid, time, xml.etree.ElementTree as ET

session = zenoh.open(config)  # config from onboarding bundle's first-publisher.py

while True:
    for track in get_tracks():
        cot_xml = render_cot_xml(track)         # has uid=track.uid inside
        # Use the track's stable uid as the key — NOT a fresh UUID:
        session.put(f"acme/router/cot/v2/{track.uid}", cot_xml.encode())
    time.sleep(1)
# subscriber.py — live tap on every track update
import zenoh

session = zenoh.open(config)  # SAME config shape as publisher

# Verify we actually peered (footgun 3 guard):
seen_router = False
for r in session.get("@/*/router", zenoh.Queue()):
    seen_router = True
    break
if not seen_router:
    raise SystemExit("session.get('@/*/router') returned nothing — TLS handshake probably failed silently")

def on_sample(sample):
    print(sample.key_expr, "->", bytes(sample.payload).decode("utf-8"))

# Wildcard match: any entity uid under v2:
sub = session.declare_subscriber("acme/router/cot/v2/*", on_sample)
print("subscriber declared, waiting...")

import time
while True:
    time.sleep(1)

Run the subscriber first, leave it running, then run the publisher in another shell. The subscriber should print one line per CoT track per publisher tick.

8. Quick reference: key-expression syntax

ExpressionMatches
acme/router/cot/v2The literal key acme/router/cot/v2. Nothing else.
acme/router/cot/v2/*One more segment, exactly. E.g. acme/router/cot/v2/abc (matches), acme/router/cot/v2/abc/def (does NOT match).
acme/router/cot/v2/**Any depth, including zero segments. E.g. acme/router/cot/v2 (matches), acme/router/cot/v2/abc/def/ghi (matches).
acme/**Anything under your __LEX_ORG__ prefix. The "fire hose" form.
**Everything on the entire fabric. Subscribers don't usually want this; it's what the audit log uses.

When in doubt, use /** for subscribers and a stable per-entity key for publishers (Pattern B). That covers almost all use cases without surprises.

9. Self-check before you ask for help

When something doesn't seem to work, run these in order:

  1. Did the router accept my publish? The portal's Inspector shows recent publishes. If your topic appears there, the router got your message.
  2. Is my subscriber actually peered? Run a session.get("@/*/router", q) and confirm at least one reply. If zero replies, your TLS handshake probably failed silently — check cert paths + endpoint hostname.
  3. Does my subscriber's key_expr actually match my publisher's key? Print both side by side. If publisher puts to acme/router/cot/v2/<uuid> and subscriber declares on acme/router/cot/v2 (no wildcard) — that's footgun 1.
  4. Was my subscriber running BEFORE my publisher fired? If you can't answer this for sure, run them in two separate shells and start the subscriber first.
  5. Can I session.get what I just put? If yes, the publish + storage path works. If subscribers still don't receive, the issue is purely subscriber-side (footguns 1–3).

If you've run those and you're still stuck, post in the feedback channel listed at the top of the Peering Guide with: your subscriber's session.open call and declare_subscriber line, one example key your publisher emits, and whether the symptom is "no messages received" or "wrong messages received." That's enough for someone with router access to tell you exactly which footgun you hit.
