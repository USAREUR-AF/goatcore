The thesis

A pub/sub fabric, a topic-and-asset registry, and per-__LEX_ORG__ adapters together can mediate every interaction pattern a multi-system ecosystem typically needs — without a separate API protocol layered on top. The transport stops being the integration story. The integration story becomes:

  1. Describe your data — register your topics + format + schema body in this portal.
  2. Optionally describe your capabilities — declare what your system can do, so others can find you.
  3. Optionally adapt commands back to your native interface — if you want to be taskable, run a small adapter that subscribes to your "tasks" topic and translates messages into whatever your system natively understands.

Everything else — discovery, authorization, audit, version negotiation, health visibility — falls out of the substrate. The portal is the registry. Zenoh is the wire. You own the adapter.

Three primitives

Transport

The Zenoh router. Topic-keyed pub/sub with capability-based ACL (your offline-CA cert names what you can publish where).

Registry

This portal. Per-__LEX_ORG__ identity, topic catalog, data-dictionary schema bodies, and optionally per-asset capabilities and live state.

Adapter (shim)

Your code. Subscribes and publishes on the fabric. If your system has a native command interface (serial, SNMP, vendor REST), the adapter translates between that and the fabric.

Today the portal serves Transport + Registry; __LEX_ORGS__ own the adapter side. Adapters live in your repo, not ours — the portal doesn't ship code that talks to your system natively. That stays under your control.

What an API typically does, and how pub/sub + registry covers it

If you're used to building integrations with REST or gRPC, here is how each pattern maps onto this fabric.

Typical API patternPub/sub + registry equivalent
POST /radar/123/task Publish to __LEX_ORG__/radar/123/task. The radar's adapter subscribes and translates. ACL gates who can publish.
GET /radar/123/state Subscribe to __LEX_ORG__/radar/123/state — the adapter publishes continuously. Or use a Zenoh query for the latest value.
GET /assets?capability=X Query the portal: GET /api/assets?capability=X. Returns the list of key-expressions to subscribe to.
API key / OAuth scope Per-__LEX_ORG__ offline-CA cert with URI-SAN + per-key ACL allowlist. Same per-__LEX_ORG__ identity you already get from this portal.
Webhook (server-pushes-to-client) Subscribe. Pub/sub is just webhooks turned inside out.
Versioning (/v2/radar) Already convention: __LEX_ORG__/system/.../v1, .../v2. Two versions on the wire simultaneously; consumers pick.
Rate limiting / backpressure Zenoh congestion control + per-__LEX_ORG__ publish-rate quotas at the router.
Schema / OpenAPI doc Your .proto uploaded here. Rendered at /schema.html for humans, served by API for machines. Available today
Idempotency tokens Producer puts a UUID in the payload; the adapter dedupes. Same as REST.
Long-polling / streaming / WebSocket Subscribe. This is what Zenoh is for.

Two patterns where the equivalence is not clean — listed honestly:

  • Synchronous request/response with tight latency budget. For genuine sub-millisecond RPC, you are better off with a direct unary call. The adapter can expose a localhost-only RPC port if needed; the fabric is not always the right answer.
  • External partners who require REST. Bridge VPSes terminate REST at the boundary and republish onto Zenoh inside. The pattern does not replace REST at the external surface; it eliminates it from the internal one.

Worked example: a radar that wants to be taskable

Suppose you ship a radar that today exposes a vendor-proprietary command interface (serial, SNMP, REST — pick one). You want it discoverable and taskable on the fabric without changing the radar's firmware. Here is how the same five steps you'd run in a typical API-driven integration map onto this fabric:

1. Radar powers on. Adapter (a small process on the same node as the radar) connects to the Zenoh router using your offline-CA cert (URI-SAN names the radar's identity). 2. Adapter registers in this portal: POST /api/vendors/<you>/assets with capabilities (e.g. ["tracking", "survey"]) + initial state. Optionally publishes a heartbeat on <you>/health/<asset-id> (your own namespace — the operator/control namespace ops/** is operator-write-only) so the dashboard sees it as live. 3. A gateway/consumer queries: GET /api/assets?capability=tracking. Receives the list of matching assets and their topic key-expressions. 4. Gateway publishes a SensorTask message on __LEX_ORG__/radar/<id>/task. The radar's ACL allows this gateway's cert to publish there; the router routes the message. 5. Your adapter subscribes to that task topic, translates each message into your radar's native command, executes, then publishes the resulting detections on __LEX_ORG__/radar/<id>/detection. Subscribers receive them.

Parity preserved with whatever you do today. From the radar's perspective the integration is unchanged — the adapter is the only new piece, and it lives in your repo under your control.

What this adds beyond basic pub/sub

Basic pub/sub gives you a wire between a publisher and a subscriber. Three things this thesis adds on top:

  1. Discoverability without coupling. A new subscriber asks the registry by capability and gets a list. Adding a new asset doesn't require updating any subscriber's config — the integration cost is paid once, not N×M.
  2. Bidirectional control without inventing a control plane. Commands are publishes; adapters do the translation. No new protocol, no separate firewall hole. The ACL grammar already handles "who can publish to which key."
  3. Health, audit, and operator visibility for free. Once an asset publishes a heartbeat, dashboards see it. Once a command is published, the audit-subscriber records it durably. No per-__LEX_ORG__ monitoring or audit integration required beyond the adapter.

Non-goals

  • Not replacing all APIs everywhere. External partners that require REST keep REST at the bridge boundary. Some internal services that genuinely need RPC keep that.
  • Not a new protocol. Everything here uses the existing Zenoh transport and the existing portal HTTP API.
  • Not a commitment to build all of this. This page sketches a direction. Each piece lands on its own merits.

What you can actually do today

The transport and the data-dictionary layer of this thesis are live. The capability/state/asset layer is design-only. Concretely on the trial fabric today:

  • Available now — register __LEX_ORGS__, declare topics + format + schema body, upload .proto data dictionaries, subscribe to anything on the fabric, browse the rendered schema at /schema.html, see your topics grouped on /vendor.html, watch live samples on /inspector.html.
  • Design only — capability declarations, asset entity type, per-asset live state with heartbeats, registry-driven task/command routing, AI-orchestrator consumption of the capability catalog.

If you have a use case that depends on the design-only pieces, tell us and we'll prioritize. The substrate is small and additive — the gap between "design only" and "available" is mostly a portal feature, not a new wire protocol.
