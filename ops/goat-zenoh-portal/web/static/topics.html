What's on this page

A topic is one Zenoh key expression each __LEX_ORG__ publishes under — for example, homemade-sensors/garage/temperature/v1. Registering it here tells the portal + inspector what to expect: which serialization the bytes use, which schema describes them, and a human description. The router doesn't enforce registration today; declaration is a polite contract that makes the inspector useful and the registry browseable.

Look at the synthetic notional rows below for working examples — that single __LEX_ORG__ is the operator-managed demo publisher umbrella that covers every sensor / data-service / observer / sink personality on the trial fabric. The synthetic badge on the __LEX_ORG__ row marks it. Full namespace governance + version-bump rules at Docs → Namespace.

Register a new topic

      

        The router doesn't require this — anyone with the per-__LEX_ORG__ cert can publish under
        their prefix regardless of what's in the registry. But declaring a topic here turns the
        inspector from "raw hex" into a readable decode + makes your namespace browsable to
        other __LEX_ORGS__ on the fabric.
      

      

        The key is a literal string, not a template.
        Whatever placeholder notation you see in our docs — <__LEX_ORG__>, <system>, <your-discretion> — is a fill-in-the-blank convention. The portal stores this field verbatim and matches it byte-for-byte against incoming publishes.
        


        Right: publisher emits acme/radar1/RADAR-EXAMPLE/position_attitude; you register key_pattern acme/radar1/RADAR-EXAMPLE/position_attitude. Identical strings → match → schema viewer lights up.
        


        Wrong: publisher emits acme/radar1/RADAR-EXAMPLE/position_attitude; you register acme/radar1/<system>/position_attitude. Two different strings → no match → /schema.html says "topic not found" even though your bytes are flowing.
        


        Substitute every <...> with a real value here AND in session.declare_publisher(KEY); the two must be identical.
      

      

        format: protobuf:<Name> must match a top-level message in your uploaded .fds.
        The second can't-skip rule. The portal refuses uploads with HTTP 422 format_mismatch when these disagree, naming the messages it actually found in the .fds and suggesting the most likely correction.
        


        Right: you register format: protobuf:PositionAttitude; the .fds you upload has PositionAttitude as a top-level message → upload accepted, schema viewer renders, decoded samples show fields.
        


        Wrong: you register format: protobuf:PositionAttitude; the .fds contains only Status + SoftwareVersion → upload rejected 422. Either PATCH the topic's format to one of the present messages, or rebuild the .fds with PositionAttitude as a top-level (not nested) type.
